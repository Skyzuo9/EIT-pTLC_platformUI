# 2026-05-17 修改记录

## Vision Tab 轮廓图显示问题诊断与修复（多轮）

1. **修改目标**：修复 Vision Tab 中两个问题：(a) Band 复选框取消勾选后 G-code 预览不刷新；(b) 轮廓图显示效果不够清晰（简单红色矩形框），需参照 `tlc_analyze.py` 的 `draw_band_overlay` 实现 OpenCV 增强渲染（洋红色光晕轮廓线 + 青色刮取路径 + 质心十字标记 + 带背景框波段标签）。

2. **第一轮修复 — 复选框 + G-code 预览 + CV 渲染基础设施**：
   - **复选框回调参数 bug**：NiceGUI `ui.checkbox(on_change=...)` 回调接收 Event 对象而非布尔值。原代码 `lambda checked, bid=...` 中 `checked` 实为 Event（始终 truthy），导致 `not checked` 永远为 False → 取消勾选无法移除 band。修复为 `lambda e, bid=...: ...(e.value)`，与项目中其他 `on_change` 模式一致。
   - **空选择不刷新 G-code 预览**：`_regenerate_gcode_preview` 在 `selected_bands` 为空时直接 return，不清理 textarea 和路径图。修复为清空后返回。
   - **CV 渲染基础设施**：在 `vision_service.py` 中将 `_generate_annotated_image` 重构为路由方法 + `_generate_annotated_image_cv`（OpenCV 渲染）+ `_generate_annotated_image_pil`（PIL 回退）。CV 渲染实现：
     - 双层轮廓线渲染（洋红色光晕阴影 + 核心线）
     - 双层刮取路径渲染（青色光晕 + 核心线 + 起止圆点标记）
     - 质心十字标记（白色 + 光晕）
     - 波段标签（带黑色背景框）
     - 颜色常量与 `tlc_analyze.py` 的 `draw_band_overlay` 对齐
   - **`contour_px` 数据格式修正**：原解析为 `[[x,y],...]`，实际格式为 `[{"x_px":...,"y_px":...},...]`
   - **`_draw_label_cv` 硬编码 20.0 修正**：传入 `plate_size_cm` 参数替换硬编码值

3. **用户反馈：轮廓图仍显示简单矩形框** — 入队 S002 样品后，CV 渲染路径静默失败并回退到 PIL 矩形框。

4. **第二轮诊断 — 发现三个导致 CV 渲染静默失败的 bug**：
   - **Bug 1（path_json 相对路径解析失败）**：`process_pair` 输出的 path_json 是相对于 output_dir 的相对路径（如 `vision_output/S002/xxx/band_01_path.json`），`Path(path_json_str).is_file()` 依赖 CWD，CWD 不匹配时文件找不到 → `contour_px=None` → 回退到 bbox 矩形。修复为三级解析策略：原始路径 → `case_dir.parent / path_json_str` → `case_dir / Path(path_json_str).name`。
   - **Bug 2（bbox_cm 被当作像素坐标）**：当 `contour_px=None` 时，回退代码直接使用 `bbox_cm` 值（厘米单位，如 1.0, 4.0）作为像素坐标绘制矩形，位置完全错误。修复为使用 `cm_to_px()` 转换。
   - **Bug 3（浏览器缓存）**：标注图文件名始终为 `{sample_id}_annotated.png`，浏览器缓存旧 PIL 图像，新 CV 图像无法刷新。添加 `?t=timestamp` 查询参数做缓存清除。

5. **用户反馈：轮廓图完全消失** — 第三轮问题，整个轮廓图区域变为空白。

6. **第三轮诊断 — 发现 `?t=timestamp` 缓存清除机制破坏本地文件路径**：
   - **根因**：NiceGUI `ui.image.set_source()` 处理本地文件路径时，`path?t=1234` 被当作完整文件名的一部分，该路径不存在 → 图片加载失败 → 空白。
   - **附加问题 1**：`_generate_annotated_image_cv` 无 try/except，CV 渲染异常时整个标注图生失败，PIL 回退路径被跳过。
   - **附加问题 2**：`SampleStore.get_annotated_image_path` 只搜索 `{sample_id}.png`，但实际文件名为 `{sample_id}_annotated.png`，路径不匹配导致找不到文件。
   - **附加问题 3**：`_load_existing_analysis` 中 `case_dir` 使用 `analysis_dir`，但 `process_pair` 输出在 `analysis_dir/{sample_id}/` 子目录下，路径不一致。

7. **第三轮修复**（3 文件）：

   - **`core/vision_service.py` — `_generate_annotated_image`**：为 `_generate_annotated_image_cv` 调用添加 `try/except`，CV 渲染异常时自动回退到 PIL 矩形框渲染，不再导致整个分析失败。
   - **`core/sample_store.py` — `get_annotated_image_path`**：修复路径不匹配，新增三级搜索模式：
     1. `analysis_dir/{sample_id}_annotated.png`（VisionService 生成的主路径）
     2. `analysis_dir/{sample_id}/{sample_id}_annotated.png`（process_pair case_dir 嵌套）

     - 标注图缺失时动态生成：利用已有 summary 中的 contour/path 数据调用 `_generate_annotated_image()` 生成

## 第四轮修复：双输出目录统一 + 路径解析增强（已 commit: ae1f4c5）

1. **修改目标**：修复 CV 渲染图在 Vision Tab 不显示的根本原因——ScrapeStage 与 Vision Tab 使用不同输出目录，导致分析结果分散在两处，Vision Tab 无法找到 ScrapeStage 生成的标注图。

2. **根因分析**：
   - ScrapeStage 使用 `VisionService(output_dir=Path("vision_output"))`（来自 `state.output_dir`）
   - Vision Tab 使用 `VisionService(output_dir=store.get_analysis_dir(sample_id))` = `data/samples/S001/analysis/`

   - Vision Tab 的 `has_analysis()` 和 `get_summary_path()` 只检查 `analysis_dir/summary.json`，不检查 `analysis_dir/{sample_id}/summary.json`，因此永远找不到 ScrapeStage 生成的结果

3. **修复内容**（4 个文件）：

   - **`core/vision_service.py`**：
     - 新增 `with_output_dir(output_dir)` 方法：创建使用不同 output_dir 的 VisionService 副本，保留其余参数不变。用于 ScrapeStage 切换到 SampleStore 的 analysis 目录
     - 增强 `_generate_annotated_image()` 诊断日志：summary.json 加载结果、`is_file()` 检查、CV 渲染返回 None 时的明确日志、CV 渲染异常回退日志
     - `_generate_annotated_image_cv()` path_json 四级解析策略：
       1. 原始路径（CWD 相对）
       2. `case_dir / Path(path_json_str).name`（文件名在 case_dir 下）
       3. `case_dir / "task1_task2_contours_paths" / f"{band_info.band_id}_path.json"`（contour 子目录精确匹配）
       4. `case_dir.parent / path_json_str`（父目录相对，兼容 legacy vision_output 结构）
     - PIL 回退渲染增强：标签增加 `Rf=` 和 `A=` 信息

   - **`core/stages/scrape.py`**：
     - `_analyze_vision_full()` 统一输出目录：有 SampleStore 时使用 `with_output_dir(analysis_dir)` 切换到 SampleStore 的 analysis 目录，使 Vision Tab 的 `has_analysis()`/`get_annotated_image_path()` 能找到结果
     - 无 SampleStore 时保持原始 output_dir（向后兼容）

   - **`core/sample_store.py`**：
     - `has_analysis()` 增加子目录搜索：`analysis_dir/{sample_id}/summary.json`（process_pair case_dir 嵌套）
     - `get_summary_path()` 同步增加子目录搜索

   - **`ui/sections/vision.py`**：
     - `_update_analysis_display()` 使用 `Path.resolve()` 绝对路径，避免 NiceGUI 相对路径解析问题
     - `_src_cache` 路径变化检测：仅在路径变化时调用 `set_source()`，避免相同路径重复调用
     - `_load_existing_analysis()` 清理冗余变量，修正 `case_dir` 为 `summary_path.parent`
     - `_regenerate_gcode_preview()` 无选中 band 时清空 G-code 预览（而非直接 return）
     - G-code 预览文件名包含 band ID 后缀（`_preview_{bands_suffix}.gcode`），避免浏览器缓存导致旧图像不刷新

4. **验证结果**：

## BeforePhoto Phase 3 审阅修复详情

1. **修改目标**：修复 Phase 3 审阅中发现的 4 Critical + 4 Warning + 3 Suggestion 问题，涉及 before_photo.py / scrape.py / vision_service.py / sample_store.py 四个核心文件。

2. **Critical 修复**（4 项）：
   - **Critical #2 — BeforePhotoStage 相机失败静默继续**：`_capture_before_photo()` 原代码捕获异常后设 `_before_path=None` 静默返回，导致后续视觉分析必然失败但无法追踪根因。修复为 re-raise 异常，让 `run()` 的 `except BaseException` 执行 PLC 清理。`_set_vision_state(waiting=False)` 移入 `finally` 块确保始终执行。
   - **Critical #3 — BeforePhotoStage 异常退出未清理 PLC FSM**：原代码无异常处理块，异常/取消时 PLC FSM 可能停在 Step 10/15 不归零。修复为添加 `except BaseException` 块：读取 `scrape_Step`，仅在 FSM 处于 before_photo 遗留步（0/10/15）时写 `scrape_Enable=False`，避免干扰并发中其他样品的 scrape FSM。
   - **Critical #3' — ScrapeStage 异常退出条件化 Enable=False**：同步修复 ScrapeStage，在 `except BaseException` 中读取 `scrape_Step`，仅在 FSM 处于 scrape 遗留步（0/10/20）时写 `scrape_Enable=False` + `_wait_fsm_idle()`，防止干扰 BeforePhotoStage 正在使用的同一 FSM。
   - **Critical #4 — VisionService mock_mode 绕过 before_path 校验**：mock 模式下 `before_path=None` 仍返回 `ok=True` 的模拟结果，与真实模式行为不一致。修复为 mock_mode 也校验 `before_path`（None 或无效文件 → 返回 `ok=False`），双帧唯一模式无单帧回退。

3. **Warning 修复**（4 项）：
   - **Warning #5 — BeforePhotoStage `_scrape_lock` None 未防护**：若 `stages/__init__.py` 未执行绑定，`_scrape_lock` 仍为 class-level `None`，`async with None` 触发不可读错误。修复为 `run()` 入口检查 `_scrape_lock is None` 并抛出 `RuntimeError`。
   - **Warning #6 — ScrapeStage `_analyze_vision_full` 返回值语义混乱**：`before_path=None` 和 `_vision=None` 都返回 `None`，调用方无法区分"未配视觉"与"拍照失败"。修复为：`_vision=None` → 返回 `None`（未配视觉）；`_after_path=None + _vision is not None` → 返回 `AnalysisResult(ok=False)`（拍照失败，走视觉失败分支）。
   - **Warning #7 — SampleStore `exists()` 误判目录为文件**：`Path.exists()` 对目录也返回 True，当文件名恰好匹配目录时 `cv2.imread()` 失败。修复为 `get_before_path()` / `get_after_path()` 全部改用 `is_file()`。
   - **Warning #8 — ScrapeStage `_wait_fsm_idle` 静默返回**：Reset 脉冲后若 FSM 仍未归零，原代码静默返回，导致后续任务可能错过 Enable 上升沿。修复为 Reset 后再等 200ms 确认，仍非 Step 0 则抛出 `RuntimeError`。

4. **Suggestion 修复**（3 项）：
   - **Suggestion #10 — 安全占位 G-code 硬编码字符串**：提取为模块级常量 `SAFE_PLACEHOLDER_GCODE = "G0 Z10.0\nM2\n"`，方便 PLC 侧统一识别。
   - **Suggestion #11 — 文件系统回退路径无警告**：`_try_fallback_path()` 找到文件时无日志，可能是旧文件。修复为添加 WARNING 日志提示。
   - **Suggestion — `_fsm_started` 追踪标志**：BeforePhotoStage 新增 `_fsm_started` 布尔标志，追踪 PLC FSM 是否已启动，异常清理时仅对已启动的 FSM 执行 Enable=False 清理。

5. **涉及文件**：
   - `core/stages/before_photo.py`：Critical #2/#3, Warning #5, Suggestion(_fsm_started)

   - **异步回调**：`add_done_callback` 在 stage 完成后更新状态标签 + 通知

3. **设计原则**：Debug = Production path——调试按钮使用与 Scheduler 完全相同的 `StageExecutor.execute()` 路径，零分支代码。
