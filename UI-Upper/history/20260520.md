# 2026-05-20 修改记录

## Vision Tab UI 优化与实时态归属修复

1. **修改目标**：Vision Tab 在并发场景下存在多处状态错位问题，需要在不增加重型抽象的前提下，一次性闭环以下三类需求：
   - **UI 布局重构**：把"Vision"卡片内的样品选择控件合并到下方"轮廓图"卡片，实现紧凑布局
   - **调试功能清理**：彻底移除"调试模式：手动指定路径"折叠面板（仅开发期使用，生产环境不应保留）
   - **实时 / 历史状态区分**：当前实现把"全局 live 标志"直接当作"当前视图在 live"来高亮，导致：
     - 浏览历史样品 S101 时仍橙色高亮
     - S1 进入乒乓时 Vision Tab 把样品 ID 错误地显示成 S101（用 `vision_current_sample_id` 而不是真正等待中的样品 ID）
     - live 推送的 before/after 路径会覆盖历史样品照片（串图风险）
     - 非 owner 视图也能点中"下发 G-code"按钮（误下发风险）
     - 乒乓握手完成后卡片橙色高亮不会消除（残留高亮）

2. **问题根因（第一性原理）**：
   - **单字段过载**：原设计中 `state.vision_current_sample_id` 同时承担两种语义——"用户在 UI 下拉框选中的样品"与"执行流推送的当前乒乓样品"。BeforePhotoStage / ScrapeStage 推图像时直接覆盖该字段，导致用户视图被强行抢占
   - **缺少归属判定**：`refresh_vision()` 把 `vision_scrape_waiting` 等系统级 live 标志直接用于 UI 高亮，未与"当前视图样品 == 真正等待样品"做合取
   - **NiceGUI style API 误用**：`element.style("")` 第一个位置参数语义是 `add`（追加），传 `""` 等于"追加空字符串"，**不会**清除已有的内联样式。要清除必须用 `style(replace="")` 或 `style(remove="...")`

3. **修复方案（第一性原理 + 奥卡姆剃刀）**：
   - **双字段分离**：新增 `state.vision_waiting_sample_id` 作为执行流权威字段（由 BeforePhotoStage / ScrapeStage 写入），与 UI 选中字段 `vision_current_sample_id` 完全解耦。BeforePhoto / Scrape 不再覆盖用户的当前选中样品
   - **派生 view 字典**：新增 `_compute_view_state(state)` 函数，在 `refresh_vision()` 入口计算 `is_owner` / `owner_scrape` / `owner_bphoto` / `is_live_for_view` / `other_live` 等派生字段；所有 UI 决策（卡片高亮、banner 文案、按钮启用、跳转可见性）统一从这一份字典消费，避免散落判定
   - **owner 守卫双保险**：`refresh_vision()` 中 `confirm_btn` 仅当 `view["owner_scrape"]` 才启用，`_on_confirm_gcode()` 入口也加同样的合取守卫，防止 enable 状态切换的窗口期被抢点
   - **图像源 owner 判定**：before / after 图像在 owner 视图用 live 推送路径（`vision_before_photo_path` / `vision_scrape_after_path`），非 owner 视图只用 `analysis_result` 中的历史路径，从根本上禁止串图
   - **NiceGUI style 清除修复**：`analysis_card.style(replace="")` 替换原 `analysis_card.style("")`

4. **核心改动**（6 件 tracked 文件）：

   - **`UI-Upper/ui/state.py`**：
     - 新增字段 `vision_waiting_sample_id: Optional[str]`（执行流权威）
     - 删除调试残留字段 `_manual_before` / `_manual_after`

   - **`UI-Upper/ui/sections/vision.py`**（核心改动 +293 / -87）：
     - 删除"调试模式：手动指定路径"折叠面板及 `_on_manual_paths` 函数
     - `render()` 把样品选择 + 分析按钮合并到 `analysis_card`，新增 status_banner 与 jump_btn（"切换到实时样品"）
     - 新增 `_compute_view_state()` 派生函数
     - 重写 `refresh_vision()`：使用 view 字典统一驱动卡片样式 / banner / 按钮启用 / scrape_indicator 文案；scrape_indicator 文案改用 `view["wait_id"]` 而非 `vision_current_sample_id`
     - before / after 数据源加 `use_live_paths` 闸门：仅 owner 视图取 live 路径
     - `_on_confirm_gcode()` 入口加 owner 守卫
     - `analysis_card.style(replace="")` 修复样式清除
     - `_on_analyze` 移除手动路径优先逻辑

   - **`UI-Upper/core/stages/before_photo.py`**：
     - 推送图像时改写 `vision_waiting_sample_id`，不再覆盖 `vision_current_sample_id`
     - 完成后清理时仅当 `waiting_sample_id == self._sample_id and not vision_scrape_waiting` 才清空（避免误清 ScrapeStage 写入的值）

   - **`UI-Upper/core/stages/scrape.py`**：
     - `_push_to_vision_tab()` 改写 `vision_waiting_sample_id`
     - `_wait_for_band_selection_and_generate_gcode()` 的 `finally` 中追加 `state.vision_waiting_sample_id = None`，确保乒乓完成或异常退出时权威字段被清

   - **`UI-Upper/ui/app.py`**：
     - `vision_state` 脏检查字段补 `current_sample` / `waiting_sample`，确保用户切换样品或执行流写入权威字段时 banner 立即刷新

   - **`UI-Upper/config.example.yaml`**：
     - PLC URL 默认切回 Mock 地址（开发期约定）；实机地址保留为注释

5. **验证结果**：
   - `py_compile` 全部通过（`vision.py` / `app.py` / `state.py` / `before_photo.py` / `scrape.py`）
   - 逻辑验证（对应截图场景）：浏览 S101 + S1 进入乒乓 → 卡片不再橙色，banner 灰色"○ 另有样品 S1 正在实时分析"，"切换到实时样品"按钮可见；切到 S1 后卡片橙色 + banner 橙色 + confirm_btn 启用；乒乓完成后 `vision_scrape_waiting=False` + `vision_waiting_sample_id=None` → `is_live_for_view=False` → 卡片样式正确清除回归默认（`style(replace="")` 修复）

6. **已知问题与后续计划**：
   - 实机端到端验证：建议在 mock 模式下并发跑 2 个样品，观察一个进入 ScrapeStage 乒乓时 Vision Tab 浏览另一个样品的高亮 / banner / 跳转按钮表现是否符合归属语义
   - 跨标签页一致性：`vision_waiting_sample_id` 仅 Vision Tab 消费；后续若 Queue Tab 需要展示"哪个样品在乒乓"，可直接读取该字段
   - AGENTS.md 已同步两条 Known Pitfalls：双字段语义 + NiceGUI `style("")` 不清除已有样式
