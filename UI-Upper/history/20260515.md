## 并发样品状态区分 WAITING/RUNNING + CancelledError 安全处理

1. **修改目标**：解决并发模型下多样品同时运行时的状态混淆问题——等锁样品与实际驱动 PLC 的样品在 UI 上均显示为 RUNNING，用户无法区分也无法安全取消；CancelledError 未被捕获导致 STAGE_DONE 事件缺失，工位永久卡 running。
2. **核心改动**（12 文件，188+/296-）：
   - `base.py`：STAGE_START 从 `execute()` 移除，新增 `_emit_stage_start()` 由子类在持锁后调用（方案A），确保事件流与实际硬件占用对齐——等锁期间不标记工位为 running；`execute()` 捕获 `CancelledError`（Python 3.9+ BaseException 子类，不被 `except Exception` 捕获），发出 `status=CANCELLED` 的 STAGE_DONE 事件，防止工位永久卡 running
   - `scheduler.py`：新增 `cancel_running_sample(sample_id)` 方法，通过 `task.cancel()` 触发 CancelledError 中断等锁样品
   - `queue.py`：新增 `_is_sample_actively_running()` 函数（扫描 log_store 事件流判断最近阶段事件是 STAGE_START 还是 STAGE_DONE），区分 WAITING（等锁/等资源未驱动 PLC）与 RUNNING（实际驱动 PLC）两种 UI 显示态；WAITING 样品可安全取消（无 PLC 副作用），RUNNING 样品不提供取消按钮（PLC 侧清理未实现）；`_cancel_sample()` 重写支持 PENDING 和 WAITING 两种取消路径；状态徽章新增"等待中" amber 色
   - `stage_state_registry.py`：并发安全修复——仅当 DONE/STEP_START/STEP_SKIPPED 的 sample_id 与当前工位持有者匹配时才更新状态，避免 A 样品的 DONE 覆盖 B 样品的 running；CANCELLED 状态也归入 error 显示
   - `state.py`：`active_sample_ids` 正式声明为 dataclass 字段 `field(default_factory=set)`，删除 `getattr(state, 'active_sample_ids', set())` 兜底代码
   - `app.py`：移除 `active_sample_ids` 的 `getattr/hasattr` 防御性代码，直接使用属性
   - `header.py`：当前样品展示从单值 `current_sample` 改为展示所有活跃样品 ID 集合
   - `flow.py`：无运行阶段时停止 1s 刷新（返回不调用 `flow_content.refresh()`），由 app.py `_periodic_refresh` 脏检查驱动，减少 CPU 开销
   - `config.example.yaml`：默认 URL 切回 `localhost:4840`（开发模式）
   - `collect.py / develop.py / spotting.py`：在持锁后调用 `self._emit_stage_start()`
   - `scrape.py`：直接调用 `self._emit_stage_start()`（无互斥锁）
   - 清理：移除 `plc_develop.txt`（已迁至 `[pending]` 前缀文件），从 git 移除 `vision_service.cpython-311.pyc` 缓存
3. **实验结果**：commit 36ad89d，16 文件变更，并发安全修复覆盖 WAITING/RUNNING 状态区分 + CancelledError 事件补全 + StageStateRegistry 样品交叉覆盖
4. **已知问题**：实际驱动 PLC 的 RUNNING 样品取消按钮暂不提供（需 PLC 侧安全中断协议支持）
5. **后续计划**：B3 scrape 工位电平范式平移；实机联调验证并发场景下状态区分正确性
