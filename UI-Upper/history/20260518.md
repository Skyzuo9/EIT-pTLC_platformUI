# 2026-05-18 修改记录

## 多Band刮取并发控制修复：RecipeTask 外层持有 _scrape_lock

1. **修改目标**：修复多 Band 连续刮取-收集序列中的并发控制缺陷——先后入队样品 A 和 B 时，样品 A 首次 ScrapeStage 释放 `_scrape_lock` 后进入 CollectStage，样品 B 可抢占 scrape 工位，导致样品 A 的重刮（selected_bands[1:]）被阻塞。

2. **问题根因**：`_scrape_lock` 的持有粒度是"单次 ScrapeStage 执行"，但多 Band 场景的物理需求是同一样品在整个 scrape→collect 序列期间持续占用 scrape 工位硬件。锁释放间隙被其他样品抢占，违反了硬件独占权的物理约束。

3. **修复方案（第一性原理 + 奥卡姆剃刀）**：
   - **核心原则**：`_scrape_lock` 保护的是 scrape 硬件（FSM）的独占访问权。多 Band 刮取是同一块硅胶板上的连续操作，物理上不可分割——必须持续占用硬件直到所有 Band 刮取完成
   - **方案**：RecipeTask 在 Phase 2-4（整个 scrape→collect 序列）外层持有 `_scrape_lock`，ScrapeStage 通过 `skip_lock=True` 跳过自身的锁获取
   - **为什么不在单 Band 时释放锁**：首次 ScrapeStage 执行完毕后才知道 Band 数量，若此时释放锁再按需重获，存在竞态窗口（其他样品可抢占），因此统一在 RecipeTask 外层持有是最简方案

4. **核心改动**（2 文件 + 2 文档）：

   - **`core/stages/scrape.py`**：
     - `__init__()` 新增 `skip_lock: bool = False` 参数
     - `_fsm_started` 从局部变量改为实例属性（供 `_run_scrape_body()` 设置、`run()` 的异常清理读取）
     - `run()` 重构：条件锁包装——`skip_lock=True` 时直接调用 `_run_scrape_body()`，`skip_lock=False` 时在 `async with _scrape_lock:` 内调用
     - 提取 `_run_scrape_body()` 方法：包含原 `run()` 内 `async with _scrape_lock:` 块内的全部 FSM 执行逻辑
     - `except BaseException` 异常清理逻辑不变（使用 `self._fsm_started` 替代原局部变量）

   - **`core/task.py`**：
     - `RecipeTask.run()` Phase 2-4 外层包裹 `async with ScrapeStage._scrape_lock:`
     - 首次 ScrapeStage 和重刮 ScrapeStage 均传入 `skip_lock=True`
     - CollectStage 不受影响（使用独立的 `_collect_lock`）
     - `_build_executor()` 新增 `skip_lock` 参数透传至 ScrapeStage

   - **`AGENTS.md`**：
     - "Other Class-Level Locks" 中 `_scrape_lock` 描述新增 RecipeTask-level lock holding 说明
     - "Known Pitfalls" 新增"Multi-band scrape: RecipeTask-level _scrape_lock holding"条目

5. **并发时序（修复后）**：
   ```
   Sample A: RecipeTask 持有 _scrape_lock
     ├── Phase 2: ScrapeStage(skip_lock=True) → 刮取 band[0]
     ├── Phase 3: CollectStage → 收集 band[0]（_collect_lock，无冲突）
     ├── Phase 4: ScrapeStage(skip_lock=True) → 刮取 band[1]
     │          CollectStage → 收集 band[1]
     └── ... → 释放 _scrape_lock

   Sample B: 尝试进入 before_photo/scrape → 在 _scrape_lock 上排队等待
     （spotting/develop 使用不同锁，可并行执行）
   ```

6. **安全保证**：
   - **异常安全**：`async with` 确保 `_scrape_lock` 在异常/Cancel 时自动释放
   - **无死锁**：`_scrape_lock` 和 `_collect_lock` 完全独立，不嵌套
   - **向后兼容**：`skip_lock=False`（默认）用于 Debug Tab 和 SampleTask，行为完全不变
   - **方案A 语义保持**：`_emit_stage_start()` 仍在持锁后调用

7. **实验结果**：AST 语法验证通过（scrape.py + task.py）。**未经 mock 端到端验证**——多样品并发多 Band 刮取的完整链路尚未实际运行验证。

8. **已知问题**：
   - 单 Band 场景下，`_scrape_lock` 在 collect 阶段也被持有（略微降低并发度），但 collect 通常耗时较短，影响可忽略
   - 多样品并发多 Band 刮取的 mock 端到端验证待做
   - **后进先出（LIFO）develop 流程未验证**：DevelopStage 的多 tank 资源分配与后进先出释放逻辑在多样品并发场景下是否正确
   - **全流程 scrape 流程未验证**：从 spotting → before_photo → develop → scrape（含拍照+视觉分析+band选择+G-code生成+刮取运动）的完整链路在 mock 环境下尚未端到端跑通

9. **后续计划**：
   - Mock 端到端多 Band 并发验证（多样品 + 多 Band 选择 → 首次 scrape → collect → 重刮循环）
   - 验证后进先出 develop 流程在多样品并发下的正确性
   - 验证全流程 scrape 流程（含 PhotoMode=0 拍照 → 视觉分析 → band 选择 → G-code → 刮取运动）

## Phase 0 E-Stop 审阅修复（11项：C1-C3 / W1-W5 / S1-S3）

1. **修改目标**：基于 Phase 0 E-Stop 安全停车体系审阅报告，修复 3 项 Critical、5 项 Warning、3 项 Suggestion 问题，确保急停链路可靠性和 Recovery UI 功能完整性。

2. **问题根因**：
   - **C1**：`PLCClient._heartbeat_loop` 用 `await self._on_estop()` 调度急停回调，`broadcast_estop` 内部遍历 task 调用 `cancel()` 可能耗时 >100ms，阻塞心跳触发虚假重连
   - **C2**：`sync_states()` 无条件用 PLC 值覆盖本地状态，`NEEDS_DRAIN(91)` 被 PLC 的 `ERROR(90)` 覆盖，Recovery UI 丢失排液跟踪
   - **C3**：Queue Tab / Flow Tab 缺少 `ESTOP`/`CANCELLED` 状态颜色标签映射，急停样品显示为灰色未知状态
   - **W1**：Header "Reset E-Stop" 按钮直接调用 `reset_estop()` 绕过 Recovery 三段式安全闸门
   - **W2**：`recovery.py` 中 `except asyncio.TimeoutError` 无法捕获 Python 3.9/3.10 的内建 `TimeoutError`
   - **W3**：排液后 `_release_btn_update()` 未被调用，"解除急停"按钮仍灰显
   - **W4**：Mock `mark_tank` 向 PLC 节点写入 PC 侧内部值 91，违反 Mock Isomorphism
   - **W5**：Recovery Tab 引用缺失时急停自动切换静默失败无日志
   - **S1**：`manual_release()` 未校验缸状态是否为 NEEDS_DRAIN
   - **S2**：排液超时后用户可重复点击，PLC Drain_Enable 反复置位
   - **S3**：`NEEDS_DRAIN=91` 枚举值注释缺少数值比较风险警告

3. **修复方案（第一性原理 + 奥卡姆剃刀）**：
   - **C1**：`await` → `asyncio.create_task()` fire-and-forget，心跳线程不再阻塞
   - **C2**：`sync_states()` 中跳过本地 `NEEDS_DRAIN` 缸，不被 PLC 值覆盖
   - **C3**：Queue Tab / Flow Tab 补充 ESTOP/CANCELLED 颜色、标签、图标、边框色、提示文本
   - **W1**：Header 按钮改为导航到 Recovery Tab（"前往 Recovery Tab"），不再直接 reset；`_tab_panels`/`_tab_recovery` 存入 AppState
   - **W2**：`except asyncio.TimeoutError` → `except (asyncio.TimeoutError, TimeoutError)`
   - **W3**：排液成功后调用 `_release_btn_update()` 刷新按钮状态
   - **W4**：Mock help 和代码注释标注 91 是 PC 侧虚拟值（实机 PLC 不会产生）
   - **W5**：急停切换 Recovery Tab 失败时输出 `log.error`，不再静默
   - **S1**：`manual_release()` 入口检查 `info.state is not NEEDS_DRAIN` 则抛 RuntimeError
   - **S2**：排液超时后 `btn.disable()` 防止重复置位 PLC Drain_Enable
   - **S3**：枚举注释改为"PC 侧虚拟状态（不对应 PLC Tank_State，禁止数值比较）"

4. **核心改动**（8 文件）：
   - **`core/plc_client.py`**：`_heartbeat_loop` 中 `await self._on_estop()` → `asyncio.create_task(self._on_estop())`
   - **`core/resource_manager.py`**：`sync_states()` 增加 NEEDS_DRAIN 跳过逻辑；`manual_release()` 增加前置状态校验；`TankStatus.NEEDS_DRAIN` 注释增强
   - **`ui/sections/queue.py`**：`_STATUS_COLOR` / `_STATUS_LABEL` 增加 ESTOP/CANCELLED 条目
   - **`ui/sections/flow.py`**：`_EVENT_STATUS_COLOR` 增加 ESTOP/CANCELLED；`_STAGE_STATE_COLOR` 增加 estop；`_render_stage_card` 增加 estop 边框色+提示文本；甘特视图增加 ESTOP/CANCELLED 图标
   - **`ui/sections/header.py`**：`_estop_reset()` → `_estop_goto_recovery()`；按钮文案+图标改为导航式
   - **`ui/sections/recovery.py`**：`except (asyncio.TimeoutError, TimeoutError)`；排液成功后 `_release_btn_update()`；超时后 `btn.disable()`
   - **`ui/app.py`**：`_tab_panels`/`_tab_recovery` 存入 state；Recovery Tab 引用缺失时 `log.error`
   - **`mock/plc_server.py`**：mark_tank help 文本和代码注释标注测试辅助性质

5. **验证状态**：⚠️ **功能暂未验证**——所有修复为代码层静态分析确认正确，未经 mock 端到端急停触发→Recovery 向导→解除急停的完整流程验证。

6. **已知问题**：
   - Header 急停导航按钮依赖 `_tab_panels`/`_tab_recovery` 存入 AppState 的时机（`_build_page` 执行后），若页面尚未构建完成时触发急停则回退到 notify 提示
   - `asyncio.create_task()` 调度的 on_estop 回调异常不会被心跳循环捕获（仅影响调度失败时的日志），不影响急停信号本身的传播
