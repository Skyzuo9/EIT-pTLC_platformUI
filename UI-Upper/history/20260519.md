## 实机调试增强：BadNotWritable 精准定位 + G-code 短指令调试开关

1. **修改目标**：实机测试中通过 UI 下发 G-code 时遭遇 OPC UA 写入错误 `The access level does not allow writing to the Node.(BadNotWritable)`，但 PLC 工程师确认 `scrape_gcode_instructions` 已勾选读写权限。需要在不增加业务逻辑的前提下，提供两项最小调试能力：
   - **精确定位**：日志中明确暴露**哪个节点**报错（不仅是 ScrapeStage 的 fallback 错误）
   - **二分验证**：通过开关切换长 G-code / 短指令，区分错误是节点权限问题还是 STRING(128) 长度超限

2. **问题根因（实机调试结论）**：
   - 上位机生成的 G-code 为 **2438 字节**，远超 PLC 端 [`plc_scraping.txt`](../../PLCsoftware/OPCUAtest/plc_scraping.txt) L92 的 `scrape_gcode_instructions : STRING(128)` 容量上限
   - **关键发现**：汇川 / CODESYS 的 OPC UA 服务器在收到长度超过 `STRING(N)` 上限的写请求时，**返回 `BadNotWritable`（0x803B0000）而不是标准的 `BadOutOfRange`**——这是非标但实测稳定存在的行为
   - 因此 BadNotWritable 在汇川实机上**不能直接判定为 AccessLevel 缺失**，必须通过短指令二分验证

3. **修复方案（第一性原理 + 奥卡姆剃刀）**：
   - **不动业务逻辑**：写入路径、错误传播、FSM 行为完全不改
   - **诊断点最少化**：仅在 `_write` 添加一处 try/except 兜底捕获 `UaStatusCodeError`，打印节点名 + VariantType + value_len + status code，重新抛出
   - **调试开关用环境变量驱动**：`SCRAPE_DEBUG_SHORT_GCODE=1` 时把长 G-code 临时替换为 `SAFE_PLACEHOLDER_GCODE`，避免在 vision.py 上做"可编辑文本框"等架构级变更

4. **核心改动**（2 文件）：

   - **`core/plc_client.py`**（`_write` 方法）：
     - 包裹 `try / except ua.UaStatusCodeError`：捕获节点级 OPC UA 错误时打印 `node=<name> vtype=<type> value_len=<len> status=0x<code> (<exc_class>)`
     - 异常仍向上抛出，对现有控制流零影响
     - 仅在异常路径执行，正常写入零开销

   - **`core/stages/scrape.py`**（新增模块级 helper）：
     - 新增 `_maybe_debug_override_gcode(gcode_text, sample_id)` 函数：环境变量 `SCRAPE_DEBUG_SHORT_GCODE=1` 时把 G-code 替换为 `SAFE_PLACEHOLDER_GCODE`（"G0 Z10.0\nM2\n"，12 字节）
     - 在两条会下发"长 G-code"的路径调用：重刮模式（L246-L248 后） + 视觉成功模式（L283-L285 后）
     - `SAFE_PLACEHOLDER_GCODE` 占位路径不挂钩（本来就是短指令）

5. **验证结果**：✅ **实机端到端验证通过**
   - 不开调试开关：日志精确显示 `[PLC] _write 失败 node=scrape_gcode_instructions vtype=String value_len=2438 status=0x803B0000 (BadNotWritable)`，确认错误来自 G-code 写入
   - 开调试开关 (`SCRAPE_DEBUG_SHORT_GCODE=1`)：写入成功，PLC FSM 正常推进到 Step 30——证明权限 OK，根因是 STRING(128) 长度超限

6. **已知问题与后续计划**：
   - **PLC 端待修**：[`plc_scraping.txt`](../../PLCsoftware/OPCUAtest/plc_scraping.txt) L92 `scrape_gcode_instructions : STRING(128)` 需扩到 `STRING(4096)` 或改为 `ARRAY[1..N] OF STRING(256)` 分段，参考 `Sampling_bubble_instructions` 的数组建模。该改动归 PLC 工程师，配合上位机此次诊断增强即可定位
   - **汇川 OPC UA 错误码非标行为**：已写入 AGENTS.md Known Pitfalls 与 common_pitfalls 记忆，避免后续同类问题再被误判为 AccessLevel 问题
   - **调试开关用法**（PowerShell）：`$env:SCRAPE_DEBUG_SHORT_GCODE = "1"; python UI-Upper/main.py --config UI-Upper/config.example.yaml`；不再调试时 `Remove-Item Env:SCRAPE_DEBUG_SHORT_GCODE`

## 展开阶段排液并发模型纠偏：Phase 3 去锁 + GroupLock 语义收敛到 prep

1. **修改目标**：上轮实机调试后发现原设计中对“展缸排液”的并发语义表述与实际流路不一致。需要根据带图例的完整流路图重新校准三件事：PC 侧锁范围、三份文档描述、并与 PLC ST 现状保持对齐。

2. **问题根因（硬件拓扑重新认识）**：
   - 实际流路图（1 组 = 4 缸 + 1 注射泵 + 1 真空泵 + 1 真空废液瓶，2 套独立设备）显示：
     - **上液 Phase 1**：同组 4 缸共享 1 台注射泵 → 必须串行（`_group_locks[group]` 取这里）
     - **排液 Phase 3**：每缸出口独立二通阀 → 真空废液瓶（缓冲罐，稳态负压）→ 真空泵；多缸同开二通不会互抢负压→ **8 缸可全部并行排液**
   - 中间曾考虑过“组内串行”的错误推论（误以为废液主管会互抢负压），用户及时纠偏 → **本轮代码/文档未在错误路线上产生任何修改**
   - 原 `develop.py` Phase 3 仍在持 `_group_locks[target_group]`——这是一个“过度串行”的存存 bug，物理上本可 8 缸同时排液，但实现上成了同组轮排

3. **修复方案（第一性原理 + 奥卡姆剃刀）**：
   - **PC 侧仅 1 处实质改动**：develop.py Phase 3 去掉 `async with DevelopStage._group_locks[target_group]`，排液仅走 `trigger_drain` + `await_drain_done`。锁类属性保留，Phase 1 prep 仍持锁（同组注射泵互斥依然需要）
   - **PLC 侧零改动**：`plc_develop_drain.txt` 现状本就是 per-tank 独立计时 + `anyDraining` 全局聖启真空泵，恰恰对应“8 缸并行”语义

4. **核心改动**（3 件 tracked 文件）：

   - **`UI-Upper/core/stages/develop.py`**：

     - `_group_locks` 类属性注释从“流路互斥”纠正为“上液阶段注射泵互斥（排液不持）”
     - Phase 1 内部加三行注释明确 GroupLock 仅覆盖 prep（Step 10/20/30）、排液阶段为什么可并行
