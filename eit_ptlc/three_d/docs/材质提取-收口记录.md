# CAD 材质提取 —— 收口记录

2026-07-31

## 要回答的问题

> "去看一下 SolidWorks 里面现有哪些材质区别的, 把它映射过来"

## 答案: CAD 里几乎没有材质区分可映射

这台设备在 SolidWorks 里本来就是一片白灰。证据三条, 彼此独立:

| 证据 | 数字 | 来源 |
|---|---|---|
| 整机渲染图里带饱和度的像素 | **1.94%**, 其余全是灰阶 | `work/previews/cad_isometric_v.png` 的色彩直方图 |
| 组件级材质名 | **0 / 1544** | `work/materials_from_cad.json` |
| 组件级外观覆盖 | **3 / 1544** | 同上 |

画面里真实存在的颜色只有三处:

- **米黄 `#E2D795`** —— 线槽立柱, 材质是 `自定义材料|优力胶`(聚氨酯)
- **青色 `#00D0D0`** —— 少量气管接头, 占比不到 0.02%
- **三个透明件** —— 门板 α=0.4、平面展缸石英玻璃 α=0.4、下相机盖板玻璃 α=0.75

零件层确实有真材质(头 20 个零件里就读出 `优力胶` 与 `solidworks materials|6061 合金|21`,
以及 `#E2D795 / #E5EAED / #AFAFAF / #FFFFFF / #7FA1B4` 五种颜色), 但种类就这么几种。

**结论**: 把 749 个零件全部取完, 收益是把兜底灰的那 1438 个网格分成大约五组
(6061 铝 / 优力胶 / 少量不锈钢 / 三块玻璃 / 其余)。真实性会好一点, 但**它不是让画面
好看的主要杠杆** —— 那个杠杆是按零件名与功能的语义赋材。

## 走过的四条路, 死了三条

| 路径 | 结果 | 判据 |
|---|---|---|
| STEP AP214 带外观 | **死** | `swStepAP` 与 `swStepExportPreference` 遍历 0~3, 8 次导出的 `FILE_SCHEMA` 全是 `CONFIG_CONTROL_DESIGN`(AP203), `COLOUR_RGB`/`STYLED_ITEM` 计数全为 0。偏好项回读确认已设进去, 导出器不读它 |
| 直读 `.SLDPRT` 二进制 | **死** | 材质名不是明文, 8 个样本零命中 |
| 逐零件 `OpenDoc6` + `CloseDoc` | **成本失控** | 能拿到真数据, 但 **34.9 秒/零件**, 749 个要 7.3 小时 |
| 递归遍历 + 批量解析 | **可用, 但会撞上自旋** | `ResolveAllLightWeightComponents` 一次 46 秒解决轻量化, 之后每个 `GetModelDoc2` 命中内存, 200 个组件仅 10 秒。跑到第 600 个组件(391 个唯一零件)时撞上自旋 |

### 自旋是这次真正的拦路虎

`IAssemblyDoc::GetComponents(False)` 必现自旋; 递归遍历里也有某个组件的 `GetModelDoc2()`
会自旋。特征是 **CPU 满一个核、内存不涨、磁盘读速几百 B/s、无模态框、`Responding=True`**
—— 只看"进程有响应"会误判成正常。

更麻烦的是**掐掉客户端不一定能止损**: 第一次掐完 CPU 立刻归零, 第二次却又空转了半小时
才自己恢复。而强杀过客户端之后, **SolidWorks 的 COM 服务端会僵住, 新的 `connect()` 永久
阻塞**(实测 100 秒超时仍未返回), 此时进程本身却显示空闲且响应正常。

**唯一的恢复手段是重启 SolidWorks。**

## 交付物(都已就绪, 可复用)

### 取数侧
- `mcp_servers/sw_mcp/extract_part_colors.py` —— 递归遍历取材质。带三重保护:
  每读 50 个零件增量落盘、把"正在读哪个"实时 fsync 进 `work/part_colors.trace.log`
  (卡死时最后一行就是元凶)、支持 `--skip` 绕开与 `resume` 续跑
- `mcp_servers/sw_mcp/server.py` 新增 MCP 工具 `sw_extract_materials`
  (**需重启 MCP 服务进程才会生效**; 当前进程加载的仍是旧版 `sw_core`)
- `sw_core._wrap(..., force=True)` —— 同一文档对象在 `IModelDoc2` 与 `IAssemblyDoc`
  之间换接口所必需

### 管线侧
- `pipeline/material_semantics.yaml` —— 新增 `MAT_URETHANE`(优力胶)与
  `glass_from_transparency`(透明件观感参数)
- `pipeline/build_materials.py` —— 把 CAD 数据转成 `materials.yaml`。三处关键处理:
  - **透明度单独成段**(门板是钣金件却透明, 不能被材质名规则盖掉)
  - **零件名发三种写法**: 原名 / slug / `[:47]` 截断 —— 实测覆盖 GLB 里 **98.4%** 的带网格节点
  - 键名统一成 `name`(语义表对人用 `id`, 下游读 `name`, 不转会 KeyError)
- `pipeline/blender_clean.py::assign_materials` —— 四级优先级:
  `功能覆盖 > CAD 透明 > CAD 材质 > 名称规则 > 兜底`

### 已验证
用 20 个零件的真实数据跑完整条重建链:

```

预算门禁: 16.31 MB / 82 绘制调用 / 2,633,413 三角形 —— 全通过
```

## 数据现状

`work/part_colors.json` 里只有 **20 个零件**(唯一一次完整落盘的那批)。
中途跑到 391 个唯一零件的那轮因为只在结束时落盘, 撞上自旋后全部丢失 ——
增量落盘正是为此补上的, 但补上之后 SolidWorks 的 COM 已经僵住, 没能再跑一轮。

## 怎么续跑(一条命令)

前提: **重启 SolidWorks**(COM 服务端已僵)。之后:

```bash
cd three_d/mcp_servers/sw_mcp
/c/ProgramData/miniforge3/python.exe extract_part_colors.py
```

会自动续跑(跳过 `part_colors.json` 里已有的零件)。若再次卡死:
看 `work/part_colors.trace.log` 最后一行, 把那个零件路径片段传给 `--skip` 再跑一次。
外面可以套 `scratchpad/harvest.sh` 那个"trace 90 秒不增长就收手"的看门狗。

数据到位后:

```bash
cd three_d/pipeline
/c/ProgramData/miniforge3/python.exe build_materials.py
/c/ProgramData/miniforge3/python.exe 03_clean_model.py --stage full --output ../work/machine.full.glb
/c/ProgramData/miniforge3/python.exe gen_twin_manifest.py
node 04_optimize.mjs --input ../work/machine.full.glb --output ../models/machine.glb
/c/ProgramData/miniforge3/python.exe 05_report.py --no-fail
```

衡量收益的单一指标: `assign_materials` 那行日志里的 **兜底数从 1438 降到多少**。

## 顺带修掉的两个隐患

1. `build_materials.py` 写出的 `functional_overrides` 与 `default` 用的是 `id` 键,
   而 `blender_clean` 读 `spec["name"]` —— 前者直接 KeyError, 后者把兜底材质命名成
   `MAT_UNNAMED`。已统一。
2. `vite-plugin-authoring.js` 的重跑管线用裸 `python`, 而本机 PATH 上第一个 `python`
   是 Windows 应用商店空壳(退出码 49、零输出), 会"成功地"什么都不做。
   已改成显式解释器路径, 可用环境变量 `PTLC_PYTHON` 覆盖。

踩到的坑已全部写进 `docs/CLAUDE.md` 硬约束第 14~21 条。
