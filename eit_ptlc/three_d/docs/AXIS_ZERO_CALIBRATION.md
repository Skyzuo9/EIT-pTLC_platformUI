# 轴零点标定规程(虚拟 ↔ 实机)

> 目标: 让三维场景里每根 PLC 轴的位置与实机反馈一一对应 —— "虚拟世界的零点对上现实世界的零点".
> 适用: 11 根 PLC 直线伺服轴. CR5 六关节已由 `calibrate_cr5.py` 最小二乘标定, 不走本规程;
> 气缸无零点概念(只有两端位), 属机构绑定阶段, 也不在本规程内.

## 1. 原理

前端把实机毫米反馈写进场景的唯一公式([MachineStateDriver.js](../../web/src/three-d/anim/MachineStateDriver.js) `setAxisMm`):

```
局部位置 = GLB加载态位置 + axis方向 · (clamp(实机mm, range_mm) − zero_offset_mm) · sign · 0.001
```

- **虚拟零点 = GLB 加载态**, 即 CAD 建模时该轴滑车所在的位姿(枢轴建在零位).
- 标零就是为每根轴确定三个参数, 全部固化在 `pipeline/rig_map.yaml` 对应轴条目:

| 参数 | 含义 | 定法 |
|---|---|---|
| `sign` | 伺服正方向与模型 `axis` 向量是否同向 | 实机向正方向 jog, 看虚拟动向; 反了翻转 |
| `zero_offset_mm` | 实机反馈等于该值时, 模型正好在 CAD 位姿 | 参考位对齐法(§3) |
| `range_mm` | clamp 边界 | **跨度 = 所骑模组行程 `stroke_mm`**, 位置按滑块实测落点解, 解不出时以控制侧示教值为锚(§5.1) |
| `stroke_mm` | 该轴所骑直线模组/导轨的物理行程 | 模组型号里的行程数字, 用 GLB 逐顶点实测交叉验证(§5.1) |

`gen_twin_manifest.py` 对 `range_mm` 做**双向**校验: 太小(盖不住控制侧示教值)与太大
(跨度超过 `stroke_mm`)都报警告, `--strict-limits` 升级为失败。

- `mmToUnit` 恒为 0.001(场景 1:1 米制), **禁止**用它吸收误差 —— 目视比例不符说明
  carriage 归属或几何错了, 不是换算错了.
- manifest 的 `_manual_` 保留机制无人使用: 标定值写进 manifest 内存态只活到刷新,
  **唯一固化真源是 rig_map.yaml**, 重跑管线只认它.
- 先例: 地轨 `axis_11y` 以实机 4 号工具位 500 mm 为零(`zero_offset_mm: 500.0`),
  现场发现 1/6 号位镜像后把 `sign` 修为 −1 —— 本规程就是把这套经验制度化.

## 2. 工具

### /calib 标定页(AxisCalibBoard 轴标定工作台)

- 入口: 导航"标定"或直接 `/calib`(旧 `?calib=1` 链接会重定向到这里).
- 工作流(2026-08-02 起, 取代早期 AxisDebugPanel 的手调零点法): **接管该轴 →
  jog 虚拟轴与实机目视对齐 → 点"匹配零点"**(公式 `zero_new = zero_old + (R − P_v)`,
  见 axisCalib.matchedZeroOffset 的推导注释) → **直接写回 rig_map**(经 dev server 的
  rigPatch 接口, 不再走剪贴板); 匹配前实机反馈落在 range 外会先提示扩界(rangeCovering).
- **匹配后的不动性校验容差 = 一个零点量化步长(`axisCalib.matchDriftToleranceM`,
  1e-3 mm × mmToUnit = 1e-6 m), 不得收紧到量化步长以下.** 2026-08-05 踩过: 阈值写死
  1e-9 m, 比它自己写入值的量化步长严 1000 倍 —— 真机的 R 是 PLC 的 REAL(小数位远不止
  3 位), 零点 `Math.round` 到 1e-3 mm 的残差折算成节点位移最大 5e-7 m, 于是"匹配零点"
  几乎必然报 `匹配校验失败(axis_1z 位移 4.95e-7 m), 已撤销 —— 请报告`, 整条标定闭环
  不可用. 单测当时没抓到, 是因为四组用例的 `zero_old + (R − P_v)` 都已是 ≤3 位小数,
  `Math.round` 退化成恒等变换. 真 bug(clamp 咬住/sign 错/认错节点)量级 1e-3 m 起,
  与本容差仍差三个数量级, 照样抓得到.
- 匹配失败时**整体回滚**(零点 + range)且**保留接管** —— 刚做完的目视对齐不该因一次
  校验失败被 feed 覆写掉; 成功才自动释放接管(下一帧用新零点覆写仍重合 = 即时验收).
- 仍保留: sign 翻转、range 编辑、"越界 clamp"红标、只在内存/刷新即回的语义.
- 非 rigged 轴不可操作 —— 先补 `carriage_members` 并重跑 `03 → gen_twin_manifest → 04`.

### console 兜底(dev 构建)

标定页挂载后有 `window.__ptlcCalib`(承接旧 `__ptlcAxisDebug` 配方, 新增接管/匹配;
方法清单见 AxisCalibBoard.vue 挂载钩子处).

### 限位一致性校验(生成期)

`gen_twin_manifest.py` 会读控制侧 `config/points/plc/*.yaml` 做**双向**校验
(`--strict-limits` 升级为失败):

- **太小**: 示教 value / 真实 limits 落在 `range_mm` 之外 → 实机走到那儿模型被静默钳在
  边界上"冻住";
- **太大**: `range_mm` 跨度超过 `stroke_mm` → 动作页滑杆与拖拽能把滑车拖出它所骑的导轨,
  观感穿模且不报任何错.

2026-08-04 按轨道行程重定十根轴后, 校验为**零警告**(此前 13 条真警告, 病根是把模组
**本体长**当成行程 —— 地轨 [0,3000] 是 900 行程的 3.3 倍、7Y [0,400] 是 100 行程的 4 倍).

### 出轨校验(`verify_axis_travel.py`)

限位校验只查 `range_mm` 的**跨度**, 查不到**位置** —— 跨度对而位置错的轴照样会把滑车推出
导轨。`pipeline/verify_axis_travel.py` 补这一刀: 按 `setAxisMm` 的公式把每根轴推到
`range_mm` 两端, 算滑块落点与实测导轨条区间比对, 出轨即非零退出。
它抓到过一次真问题: `axis_3y` 跨度 319 完全正确, 但配上 `zero_offset` 的 0.0 占位,
动作页拉到示教上界 245 会让滑块冲出导轨 **139.85 mm** —— 修法不是改 range, 而是由
"行程 319 必须覆盖控制侧 [−20, 245]"联立推出 `zero_offset` 首值 139.85。

## 3. 逐轴标零七步法

1. **前提**: 该轴已 `rigged: true`, 且离线 jog 确认随动零件组正确、方向幅度正确.
2. **定 sign**: live 模式下, 上位机手动页向**正方向** jog, 观察虚拟动向;
   反向 → 面板翻 sign(翻完当帧生效, 无需重跑).
3. **选参考位**, 优先级从高到低:
   a. 回零后的机械原点(反馈 ≈ 0);
   b. 有物理意义的示教点(§5 速查表, 如地轨六槽位、拍照位 `Photo_8Y_Target=420`);
   c. 可目视对齐的机械特征(端板贴合、对位销、卡槽入位).
4. **实机移到参考位**, 记下面板/HUD 显示的反馈值 R.
5. **live 微调 `zero_offset_mm`** 直到虚拟与实机目视重合(现场对照或照片).
   面板秒级生效; 每改一步, 模型立即按新公式重放当前反馈.
6. **第二参考位复核**(尽量取行程另一端): 防镜像 —— 地轨当年 4 号位看似正确、
   1/6 号位对调, 就是单点标定的盲区; 顺便全程走一遍, 确认无"越界 clamp"红标、无穿模.
7. **固化**: 面板"导出 YAML" → 人工回填 `pipeline/rig_map.yaml` 对应轴条目(在注释里写明
   参考位依据, 照 `axis_11y` 的写法) → 重跑 `03 --stage full → gen_twin_manifest → 04`
   → 部署 5 文件 → 刷新页面复验两个参考位 → 记入 `PTLC_ANIMATION_MASTER_PLAN.md` 台账.

**现场 jog 安全**: 按控制侧互锁跳(§5 备注列), 例如 8Y/9X 定位前须 10Z 抬起(<6 mm)、
4X/3Y 前须 5Z 抬起(<3 mm)、地轨点动前确认机械臂在安全位. 互锁由 PLC 强制, 但提前知道
能避免"jog 没反应"误判成绑定问题.

## 4. 每轴验收标准

- 方向: 正向 jog 虚拟同向, 行程两端无镜像;
- 位置: ≥2 个参考位目视重合(目标数 mm 级, 参照地轨标定 RMS 2.0 mm);
- 全程: min→max 走一遍无"越界 clamp"、无穿模;
- 记录: rig_map 注释写明参考位依据; 台账 §5.2 状态更新.

> sign=−1 时 `δ ≤ 0` 等价于 `mm ≥ zero_offset`, 一样成立, 只是 `zero_offset` 从该轴能到的
> **最大**毫米值变成**最小**毫米值.
>
> 两条不依赖目视的证据:
> ① **可行性** —— `verify_plate_seats --solve` 的 1-DOF 反解要求板托座在放板位落到
>    **δ = −80.85 mm**(让板落在机器人 P19 示教点的吸盘下). 配 OPC 实读的两个位置
>    (放板位 56.0 / 点样位 −20.0): sign=+1 需 `zero_offset = 136.85`, 点样位随即落到
>    δ = −156.85, **出 100 mm 行程 57 mm, 无解**; sign=−1 只需 `zero_offset = −24.85`,
>    放板位 δ=−80.85 ✓ 点样位 δ=−4.85 ✓, 两个示教点还各留 4.85 / 19.15 mm 余量.
>    **两个实读示教点 + 反解, 只有 −1 同时容得下.**
> ② **判据** —— sign=+1 下 `verify_plate_seats` 退出 1: `spot_seat` 法兰系 dX=+319.0,
>    而同翻转态的刮板台 P65 是 +238.1, 偏 40.8 mm(超 40 mm 容差). 订正后 dX 回到 +238.2,
>    偏离 5.4 mm, 判据转绿. 且反解虽只有 1 个自由度(沿 X 平移), dY(−8.0 vs +2.8)与
>    dZ(−26.1 vs −26.1)是白送的独立校验, 都吻合 —— 不是循环论证.
>
> 由此结论 **CAD 建模位 ≈ 点样位**(差 4.85 mm), 而不是此前写的"CAD 建模位 = 放板位".
> 完整溯源见 `工位摆位偏差溯源_20260805.md`. `zero_offset` 出自反解而非现场标定,
> **§3 七步法第 2/5 步仍须现场走一遍**.

### 5.1 `range_mm` 的定法(2026-08-04 收口)

1. **跨度恒等于 `stroke_mm`** —— 这就是"轨道范围限制"本身;
2. **位置**优先由几何直接解: 在 `work/machine.full.glb`(前端加载的那份, 零位=其加载态)
   上量导轨条净长 `L`、模组自身滑块块长 `c` 与现落点, 端块余量 `m = (L − c − stroke)/2`,
   得可动窗口 `δ ∈ [−(gap_low − m), gap_high − m]`, 再按 `mm = zero_offset + δ/sign` 换算.
   **自检**: `δ` 跨度必须等于 `stroke_mm`, 对不上就是导轨/滑块认错了, 停下重认;
3. 几何解与控制侧矛盾时(未标零的轴, `zero_offset` 还是 0.0 占位), 以控制侧
   limits/示教值为锚**最小平移**, 差值写进注释供现场标零参考, **不写进 `zero_offset`**.

自证: `axis_1z` 的几何解 [−52.4, 547.4] 与控制侧 limits [−50, 550] 两条互不相干的证据
吻合到 2.4 mm; `axis_5z` 的几何窗口整段包住控制侧 [−5, 50]; `axis_6x/7y/9x/10z` 的滑块
在 CAD 里恰停在行程端点(端块余量分毫不差), 窗口直接就是 `[zero, zero ± stroke]`.

### ⚠ 标完 `axis_11y` 必须重编译片段(`--flows`)

`gen_twin_manifest` 只更新契约, **不动已落盘的片段**, 而片段并非全是运行期换算的:

- 片段里的 `axis.to_mm` 是控制侧毫米, 由前端 `setAxisMm` 运行期换算 —— 跟着新标定走, 没问题;
- 但**机械臂位姿与载荷落点是编译期烘死的**: `scene_kinematics.RobotPosture` 把 `setAxisMm`
  在 Python 侧原样重写了一遍, 读**编译当时** `axis_11y` 的 `zeroOffsetMm/sign/rangeMm`,
  结果烘进每个片段的 `detach.dock.position/quaternion` 与 `compiled.moveLTrajectories`。

所以标完地轨不重编译, 演示里的板/托盘会落在按旧零点算的位置上, 而**画面照播、不报任何错**。

`three_d_authoring` 的 `flows` 步骤标了 `optional=True`, 因此**「全链重跑」也跳过它** ——
必须显式点名: 标定页写回走的是 `['manifest','manifest-cr5','deploy']`, 重编译要另外从
演示页的「按当前标定重新编译」按钮触发(等价 `startRebuild(['flows'])`, 约 1 分钟)。

这件事现在有自动检测: 片段的 `source.railCalib` 记着编译时的地轨标定三元组
(`clip_compiler.rail_calib_stamp`), 前端 `clipSchema.railCalibStatus` 拿它与当前契约比,
不一致就在演示栏标「待重编译」并给出重编译入口。**旧片段没有这个键, 一律判「未标记」而
不是判绿** —— 看到「未标记」就跑一次 `--flows` 补上。

> 为什么既有的 `referencePointHash` 校验抓不到: 它比的是 clip 与 `robot-points.json` 的
> SHA, 两者出自同一次 `sync_ptlc_robot` 运行, 永远自洽 —— 一起陈旧时照样全绿。
