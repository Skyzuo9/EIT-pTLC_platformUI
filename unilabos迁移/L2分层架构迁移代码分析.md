# L2 分层架构迁移：代码复用与实施设计

> 状态：当前实施主线
> 修订日期：2026-06-20
> 事实依据：最新 `PLCsoftware/OPCUAtest/*.xml`、当前 `UI-Upper/core/`、机器人 schema v2/RouteExecutor，以及已经跑通的现有工作流
> 关联文档：`PLC_L2_Workstation_Action_Decomposition.md`、`PLC_Current_Workstation_Flow.md`

## 1. 当前结论

目标架构保持为：

```text
中控系统
  → FastAPI
  → pTLC 上位机：样品流程、资源、机器人、相机和 PLC 动作编排
      ├─ PLC：工位 L2 动作、本地传感器闭环、互锁和故障处理
      ├─ 机器人：上位机直连的命名动作
      └─ 相机/CNC/视觉：上位机侧业务能力
```

当前阶段不新增通用 `ActionListExecutor`。继续由 `RecipeTask` 承担样品顶层编排，复用现有 `RouteExecutor` 执行短时机器人业务路线；PLC 侧新增统一 L2 动作通道。

迁移完成后的生产代码只保留 L2 主路径。现有已跑通 Stage 程序作为迁移基线和回退依据保留到对应工位验收结束，随后删除无意义的旧状态机、旧变量和重复判断，不长期维持两套生产逻辑。

## 2. 事实边界

### 2.1 PLC 事实源

- 最新 `PLCsoftware/OPCUAtest/*.xml` 是当前 PLC 代码事实源。
- `plc_*.txt`、`ref_plc_*.txt` 统一视为旧版或设计参考，不再用于判断当前动作是否实现。
- XML 中保留了早期 TODO 和调试批注。由于当前完整工作流已经跑通，批注本身不构成“动作未实现”的证据。
- 是否需要补错误码、超时或传感器诊断，应按最新 XML 的实际分支和现场验收结果判断，而不是按遗留注释判断。

不建立复杂的动作成熟度矩阵。每个待迁移动作只需要记录：

```text
当前 XML 来源
现有入口/完成条件
L2 目标边界
需要改造的跨工位逻辑
现场回归结果
```

### 2.2 上位机事实源

当前 `RecipeTask`、StageExecutor、`ResourceManager`、`ConsumableManager` 和机器人 RouteExecutor 都有实际调用路径。迁移前不根据文件名或粗略行数删除模块。

不再使用“约 70% 复用”“约 300 行改动”一类未经测量的估计。代码只分为：

- 保留：职责不变。
- 适配：职责保留，接口改为 L2。
- 合并：重复能力收敛到现有模块。
- 删除：替代路径验收完成后移除。
- 历史：不参与当前运行。

机器人 TCP、Modbus 和 14 条业务路线的“软件验证”与“真机验收”继续分开表述，未经现场验收的不标记为生产可用。

## 3. 上位机侧收敛方案

### 3.1 保留的核心职责

以下职责保持在上位机：

- `RecipeTask`：样品流程、多条带循环、并发启动点和异常收口。
- `plc_client.py`：OPC UA 连接、心跳、重连、序列化写入和 E-Stop 检测。
- `vision_service.py`、`camera_service.py`、`cnc_path_generator.py`：视觉、相机和路径计算。
- `ResourceManager`：8 个展缸的分配、归属、异常恢复。
- `ConsumableManager`：耗材架和暂存 A/B 的槽位账本。
- `RobotActionService`、RobotFlow/Plan/Route：机器人点位、工具、命名路径和短事务执行。
- 日志、样品文件、数据库和 UI 状态模块。

### 3.2 需要适配的路径

- `plc_client.py` 新增工位 L2 动作接口，同时在迁移期保留旧 Stage 接口。
- StageExecutor 中的参数转换、视觉、耗材决策继续复用；对 PLC 的调用逐步替换为 L2 动作。
- `RecipeTask` 在工位迁移完成后直接调用 L2 动作或机器人 Route，不预先编译完整静态 ActionList。
- `StageStateRegistry` 继续服务 UI 进度和兼容展示，但不作为物理占用的唯一事实源。
- `SampleTask`、旧 G-code 字段和旧 Stage 调用只有在调用者和 PLC 变量都完成替换后才删除。

### 3.3 不新增通用 ActionListExecutor

现有 RouteExecutor 已覆盖：

```text
PLC action / PLC wait / Robot route / Camera action
```

但它是面向短时机器人业务路线的同步事务执行器，并通过工作线程桥接 asyncio。它不应扩展为持有整个样品生命周期资源的通用执行器。

首版关系为：

```text
RecipeTask
  ├─ PLCActionClient
  ├─ RouteExecutor（短时机器人交接）
  ├─ CameraService
  ├─ ResourceManager
  └─ ConsumableManager
```

只有在多个工位迁移后确实出现稳定重复模式时，才从 RecipeTask 中抽取通用步骤执行器。

## 4. PLC 侧目标

PLC 不再决定跨工位生产顺序或机器人任务优先级，但继续拥有：

- 全局 MODE/E-Stop 安全门控。
- 工位 L2 动作状态机。
- 原始传感器、气缸、泵、阀和伺服闭环。
- 动作前置条件检查和拒绝权。
- 动作执行中的故障、超时和安全停止。
- 展缸本地 TON 超时排液保险。

迁移完成后删除：

- PLC 机器人 14 路任务优先级树。
- 上位机已经显式编排后不再使用的跨工位流程判断。
- `PhotoMode`、`IsLast` 等只服务旧整段 Stage 的路由变量。
- 已被 L2 通道替代的旧 Stage Enable/Done 入口。
- 旧程序对应的上位机兼容分支。

删除前必须保留一个可恢复的已跑通 PLC 工程基线，并完成对应工位的 L2 回归。

## 5. 工位统一动作通道

每个单实例工位使用一个动作通道；展开始终拆为一个共享 prep 通道和 8 个独立 tank 通道。

### 5.1 控制字段

```text
PC → PLC
  ActionCode
  RequestSeq
  Start
  Reset
  动作专用具名参数

PLC → PC
  State = IDLE | RUNNING | DONE | REJECTED | ERROR | INTERRUPTED
  ActiveCode
  AcceptedSeq
  LastCompletedSeq
  Step
  ErrorCode
  SafeState
  Retryable
```

设计约束：

- 不使用万能 `ParamInt[]/ParamReal[]/ParamStr` 代替现有具名参数；泵指令、CNC 数组和工艺参数继续使用明确变量。
- `Busy` 由 State 派生。
- ErrorCategory、文本消息和恢复建议由上位机错误码目录映射。
- `RequestSeq` 只用于同一 PLC 运行会话内的去重和结果关联，不代表物理动作天然幂等。
- PLC 重启或通信中断后，如果动作结果不明确，机器人取放、加液、夹持等动作不得自动重发。
- 启动时序继续使用下降沿确认：

```text
Start=FALSE
→ 等 State=IDLE
→ 写具名参数、ActionCode、RequestSeq
→ Start=TRUE
```

### 5.2 不使用专门 Confirm 协议

上位机同时管理 PLC 和机器人，因此不再需要 `WaitHost/HostContinue` 或通用 Confirm 变量。

跨设备交接使用三个普通步骤：

```text
PLC Prepare：工位进入可接收/可释放的稳定状态
→ Robot NamedAction：上位机执行机器人搬运
→ PLC Closeout：夹持、释放、传感器校验和本地状态收尾
```

Closeout 是普通 PLC L2 动作，不是“上位机确认 PLC”的协议信号。机器人 Done 只能证明机器人程序结束，不能代替 PLC 对板、瓶、收集器和气缸状态的本地校验。

不新增 `robot_req_*` BOOL。上位机已经知道下一步要执行哪个机器人动作；PLC 只需返回 Prepare 结果，并在 Closeout 中校验物理状态。

## 6. 工位动作边界

具体动作清单由 `PLC_L2_Workstation_Action_Decomposition.md` 维护。此处只规定层次：

- 上位机业务动作：例如 `Collect_LoadBottle`、`Sampling_LoadPlate`。
- PLC 本地动作：Prepare、工艺动作、Closeout、ResetFault。
- 机器人命名动作：受限来源、目的地、工具和路径。

例如：

```text
Collect_LoadBottle（上位机业务动作）
  1. Collect_PrepareBottleReceive
  2. Robot_LoadBottleToCollect
  3. Collect_SecureAndVerifyBottle
```

旧 PLC Action 可复用其内部设备动作，但必须移除被上位机接管的机器人调度和跨工位顺序判断。

## 7. 工位状态与资源管理

### 7.1 StageStateRegistry 的边界

`StageStateRegistry` 由事件流推导，适合描述：

- 当前样品正在执行哪个业务阶段。
- UI 显示 running/waiting/error。
- 阶段日志和历史。

它不能独立证明工位物理占用，因为：

- 进程重启后事件状态可能丢失。
- 动作结束后板可能继续留在工位。
- PLC 可能检测到物料存在，但上位机任务已退出。
- 展缸和暂存槽位已经有各自的权威账本。

因此不把 StageStateRegistry 改造成总资源管理器。

### 7.2 保留领域管理器，增加统一只读视图

不把所有状态合并到一个可写“大 ResourceManager”。继续保留：

- `ResourceManager`：展缸状态和 sample 归属。
- `ConsumableManager`：耗材架、暂存 A/B 和槽位。
- PLC 动作 State：工位执行状态和物理传感器摘要。
- RobotActionService：机器人 Busy、工具和当前位置状态。
- 样品状态：当前板所属样品和业务阶段。

新增轻量只读聚合接口 `SystemResourceView`，向 Scheduler、UI 和 FastAPI 提供统一快照，不拥有第二份可写状态。

物理事实与业务归属分开：

```text
PLC：是否存在板/瓶/收集器、执行器是否到位
上位机：该物料属于哪个 sample、后续应去哪里
聚合视图：一致 / 不一致 / 需要人工恢复
```

只补当前缺失的板位置记录，不复制展缸和耗材账本。

## 8. 单层调度锁

上位机使用一个动作资源门管理短期执行冲突；PLC 保留最终拒绝权。

原则：

- 一次动作原子获取完整资源集合，获取不到则等待或返回 Busy。
- 不在 RecipeTask、ParallelGroup、RouteExecutor 三层重复获取同一资源。
- 不为物料长期占用持续持有 asyncio.Lock。
- `ResourceManager` 和 `ConsumableManager` 的内部锁只保护各自数据一致性，不参与跨工位调度。
- 机器人 RouteExecutor 只在短时转运事务内持有机器人资源，并设置有限等待时间。
- Camera/CNC 如果只能通过 PhotoScrape 使用，首版由 `station:photo_scrape` 覆盖，不重复加锁。
- tool 是机器人状态，不作为独立并发锁。

首版动作资源：

```text
station:sampling
station:photo_scrape
station:collect
develop_prep
tank_action:1..8
robot
pump_command_bus
```

展缸长期归属继续由 ResourceManager 维护，不放入短期动作锁。

## 9. HMI 与控制优先级

控制优先级：

```text
E-Stop > HMI_MANUAL > L2_EXTERNAL
```

手动模式请求具有高于外部动作的优先级，但切换必须由 PLC 控制：

1. 收到 ManualRequest 后立即禁止接受新的外部动作。
2. 当前动作执行动作专用的安全停止/中断逻辑。
3. PLC 将 State 置为 `INTERRUPTED`，记录 ErrorCode/SafeState。
4. 到达允许手动控制的安全状态后，启用 HMI 手动输出。
5. 返回自动模式前必须完成 Reset/Init 和资源一致性确认。

HMI 不直接在外部动作运行中抢写同一个自动输出。真正需要立即切断危险运动时使用 E-Stop。

迁移期旧 Stage 与 L2 通过全局 `AutoControlMode=LEGACY|L2` 互斥；目标代码完成后删除 LEGACY 分支，只保留 L2 自动和 HMI 手动。

## 10. 展开 TON 保险

展开时长由上位机配方下发，PLC 每缸启动本地 TON：

```text
Tank_StartDevelop(tank_id, duration_s)
  → PLC Tank_State=DEVELOPING
  → 上位机正常监控并可提前触发 Drain
  → 若上位机未触发且 TON 到期，PLC 自动进入 DrainAndDry
```

约束：

- 上位机触发和 TON 到期必须汇入同一个幂等状态转换，排液只能启动一次。
- PLC 暴露 `DrainTriggerReason=HOST|TON_FAILSAFE`，供日志和恢复使用。
- TON 只负责单缸本地工艺保险，不参与机器人取板优先级。
- 排液完成后，上位机决定机器人取板顺序。
- 上位机仍持久化预计完成时间，用于 UI 和重启诊断；不再与 PLC 交换绝对 LREAL 时间戳。
- 若要求 PLC 重启后仍保留剩余时间，再单独评估 RETAIN；首版不为此增加复杂度。

## 11. 删除与迁移策略

目标是减少冗余，而不是永久兼容。

每个工位按以下顺序迁移：

1. 从最新 XML 提取可复用内部动作。
2. 增加统一 L2 动作通道。
3. 先迁移无机器人参与的动作。
4. 再迁移 Prepare → Robot Route → Closeout。
5. 使用当前已跑通流程做同输入、同物理结果回归。
6. 验证 HMI 手动抢占、E-Stop、Reset 和异常恢复。
7. 切换该工位到 L2 主路径。
8. 删除该工位旧 Stage 入口、机器人调度分支、旧变量和上位机兼容判断。
9. 更新 PLC 导出 XML、上位机契约、Mock 和文档。

建议顺序：

```text
Collect_Init / Collect_Elute 协议试点
→ Sampling
→ Develop prep + TankAction + TON
→ Collect 机器人交接
→ PhotoScrape
→ 删除 PLC 机器人 14 路优先级树
```

不要一开始整站重写 collect。先用一个无机器人动作验证协议，再逐步拆交接，可显著降低联调风险。
