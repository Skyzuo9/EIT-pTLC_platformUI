# pTLC 工作站对齐简要说明

## 1. 现有系统概况

pTLC 工作站当前已经具备可运行的上位机、PLC、机器人程序、视觉分析、耗材管理和样品队列调度能力。

当前系统拓扑如下：

```text
/本地操作员
    -> pTLC 上位机 UI / 后续 API
        -> Python 调度、配方、视觉、资源账本、日志
            -> OPC UA
                -> PLC 工位 FSM、安全互锁、泵/阀/气缸/CNC/机器人调度
                    -> ModbusTCP
                        -> 机器人执行取放动作
```

当前完整样品流程为：

```text
SPOTTING -> BEFORE_PHOTO 与 DEVELOP 并行 -> SCRAPE -> COLLECT -> DONE
```

系统支持多样品队列、多展缸资源、耗材槽位管理、多条色带刮取/收集、视觉识别、G-code/CNC 路径生成、日志和历史结果查询。

## 2. 当前上位机职责

pTLC 上位机主要承担：

- 样品队列和配方管理
- stage 调度：spotting、before_photo、develop、scrape、collect
- OPC UA PLC 通信
- 视觉拍照和 TLC 图像分析
- CNC 刮取路径生成
- 展开缸资源管理
- 耗材槽位账本管理
- 样品文件、图片、分析结果和日志管理
- 本地 NiceGUI 操作界面
- E-Stop 状态联动和恢复向导

当前上位机与 PLC 的通信主要是统一 stage 协议：写入参数，拉起 Enable，等待 Done/Error，并根据 WaitConfirm/Confirm 完成必要握手。

## 3. 当前 PLC 职责

PLC 当前承担确定性执行和安全边界：

- 工位 FSM
- 急停、安全互锁、限位、气压等硬条件判断
- 泵、阀、气缸、CNC 和机器人动作时序
- 机器人动作选择与授权
- 通过 OPC UA 向上位机暴露状态和完成信号
- 通过 ModbusTCP 向机器人下发 `FunctionID` 和参数

我们的设计倾向是：即使未来由中控或上位机下发更原子化动作，PLC 仍应保留安全准入和拒绝权。

## 4. 当前资源与队列逻辑

当前系统有两类主要资源账本：

- `ResourceManager`：管理 8 个展开缸的占用、释放、排液状态和异常恢复状态。
- `ConsumableManager`：管理硅胶板、粉末收集器、收集瓶、耗材架槽位和暂存位。

队列调度由 `Scheduler` 和 `RecipeTask` 负责：

- 样品入队后按配方逐 stage 执行。
- 每个 stage 通过异步锁保护对应硬件资源。
- 不同样品可以在不冲突的资源上并发推进。
- before_photo 和 develop prep 当前可并行。
- scrape 和 collect 对多色带有特殊锁策略，避免不同样品抢占刮板/拍照工位。

当前锁和资源模型是为了保证现有自动流程安全运行。如果中控希望下发原子动作，需要明确这些资源由谁占用、谁释放、动作失败后谁回滚。

## 5. 当前通信设计

当前主要通信链路：

- 上位机到 PLC：OPC UA
- PLC 到机器人：ModbusTCP
- 液位检测模块：MQTT，可选
- 上位机 UI 到浏览器：NiceGUI/WebSocket

中控接入方式目前待定。可讨论选项包括：

- HTTP REST：易调试，适合动作提交、状态查询和结果查询。
- WebSocket：适合过程状态持续推送。
- OPC UA：适合已有工业中控体系直接读写变量。
- MQTT：适合事件和状态发布，但动作确认语义需要额外设计。
- ROS2/Uni-LabOS Driver：适合后续纳入 Uni-LabOS 设备图和工作流系统。

建议先确定动作协议语义，再决定具体通信承载。这样可以避免通信方式变化时重做业务模型。

## 6. 面向中控的新接入方向

根据最新沟通，可能更希望由中控系统下发原子化动作，并由 pTLC 执行单元完成安全检查和动作执行。

因此建议新的接入方向是：

```text
中控编排实验流程
    -> 调用 pTLC 原子动作 API
        -> pTLC 上位机管理点位、参数、状态和日志
            -> PLC 做安全准入和动作执行
                -> 机器人/泵/阀/相机/CNC 完成具体动作
```

第一批可以优先讨论机器人动作 API：

- 查询机器人状态
- 查询当前位置
- 移动到命名点位
- 受限 `MovJ`
- 受限 `MovL`
- 执行业务级机器人动作，例如取放硅胶板、取放收集器、换工具

其中“受限”表示动作必须经过模式、区域、参数范围、工位占用和安全互锁检查。

同时，PLC 侧当前 stage FSM 内部的动作也可能需要进一步拆解。原因与机器人相同：中控可能希望拿到更细粒度的执行能力，并在中控侧或上位机侧二次封装成实验动作。

这类动作可以分为两种粒度：

- 大粒度工位动作：例如“拍照”。它内部可能包含伺服移动到指定拍照位、遮光气缸关闭、触发相机拍照、遮光气缸打开、伺服回位等步骤。其中伺服目标位置、曝光参数、是否回位等都可能成为动作参数。
- 小粒度执行器动作：例如打开/关闭展缸盖、单独控制遮光气缸、伺服移动到指定位置、泵/阀单步动作、读取某个工位传感器状态等。

这部分需要与进一步对齐：希望直接编排到哪一层？哪些动作由中控封装，哪些动作由 pTLC 上位机/PLC 保留为业务动作？原则上，越小粒度越灵活，但对安全互锁、资源状态一致性、异常恢复和动作时序的要求也越高。

## 7. 我们的主要考虑

### 7.1 保留现有程序

建议保留现有 pTLC 自动流程和 UI，原因是：

- 当前流程已经跑通，可作为本地生产路径。
- 中控接入初期需要 fallback。
- 本地 UI 仍适合调试、恢复、维护和状态诊断。
- 现有队列、资源账本、视觉和日志能力可以复用。

### 7.2 不建议无约束开放机器人裸指令

希望上位机掌控点位信息，这是合理的柔性生产需求。但如果直接开放无约束 `MovJ/MovL`，风险较高。

建议开放：

- 带坐标系和区域限制的移动指令
- 带速度/加速度上限的移动指令
- 带工具状态和工位占用检查的移动指令
- 带请求序号和状态反馈的动作协议

### 7.3 PLC 仍保留安全裁决权

即使中控或上位机决定要执行某个动作，PLC 仍需要判断：

- 急停是否触发
- 安全门/气压/限位是否正常
- 机器人是否 Busy
- 工作站是否被自动流程占用
- 目标点位是否在允许区域
- 参数是否越界
- 当前模式是否允许外部控制

PLC 应能返回明确拒绝原因，而不是只返回失败。

### 7.4 PLC 动作拆解需要分层开放

PLC 侧动作不建议一次性把所有内部 BOOL、气缸、阀、伺服点动都直接开放给中控。更稳妥的方式是分层开放：

- 工位业务动作：例如拍照、打开展缸、关闭展缸、准备展开、单次点样、单次刮取准备。
- 受限设备动作：例如伺服移动到指定工位坐标、遮光气缸开关、展缸盖开关、泵/阀单步动作。
- 只读状态动作：例如读取工位占用、气缸到位、伺服当前位置、盖状态、相机就绪状态。

例如“拍照”可以作为大粒度动作暴露，也可以拆为：

```text
move_servo(photo_position)
close_light_shield()
trigger_camera_capture()
open_light_shield()
move_servo(home_position)
```

两种方式各有价值。大粒度动作更安全、易恢复，也更接近当前 PLC FSM；小粒度动作更柔性，但需要中控承担更多时序和异常处理责任。建议先和一起列动作清单，再给每个动作标注开放层级、参数、前置条件、拒绝原因和恢复策略。

### 7.5 资源账本需要共同定义

原子动作接入最大的设计风险不是通信，而是资源状态。

例如中控调用“取硅胶板”后，需要明确：

- 硅胶板 ID 由谁生成和维护？
- 硅胶板从哪个槽位取出？
- 动作成功后该资源的位置由谁更新？
- 动作失败后资源状态如何回滚？
- pTLC 本地 UI 和中控状态不一致时以谁为准？

这部分需要作为对齐重点。

## 8. 建议共同确认的问题

1. 中控希望采用哪种通信方式？
2. 第一批需要开放哪些机器人动作？
3. 是否必须开放裸 `MovJ/MovL`，还是可以接受受限移动和业务动作？
4. PLC 工位动作希望开放到哪一层：完整 stage、大粒度工位动作，还是小粒度执行器动作？
5. 以“拍照”为例，希望调用一个 `capture_photo` 动作，还是希望分别控制伺服、遮光气缸和相机触发？
6. 小粒度动作的时序和异常恢复由谁负责：中控、pTLC 上位机，还是 PLC？
7. 点位数据由中控维护，还是 pTLC 上位机维护并开放编辑/查询接口？
8. 资源状态由谁维护？是否需要双方同步？
9. 外部原子动作是否允许在 pTLC 自动队列运行中插入？
10. 需要哪些过程反馈：动作状态、步骤、当前位置、工位状态、错误码、日志？
11. 是否需要权限、审计日志和模式切换确认？
12. 是否需要保留完整 pTLC 配方运行接口作为高级 API？

## 9. 建议下一步

建议先用机器人动作作为最小闭环，同时选择一个 PLC 工位动作作为拆解样例。拍照动作比较适合作为样例，因为它同时涉及伺服位置参数、气缸动作、相机触发和回位逻辑。

1. 定义动作请求/反馈统一数据结构。
2. 确认通信承载方式。
3. 定义外部控制模式和本地自动模式的互斥规则。
4. 定义机器人点位和坐标系管理方式。
5. 定义 PLC 工位动作的分层粒度：大粒度动作、小粒度动作、只读状态。
6. 定义第一批动作清单和拒绝码。
7. 在 PLC 中评估动作准入变量和反馈变量。
8. 在上位机中保留现有流程，同时增加面向中控的 API 适配层。
