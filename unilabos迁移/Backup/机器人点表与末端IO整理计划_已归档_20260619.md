> 更新日期：2026-06-18  
> 状态：当前主线实施文档。用于指导机器人固定流程向“上位机点位管理 + 原子动作 + 流程编排”迁移。

> 2026-06-18 实施进展：阶段 A 的自动导入/校验基础、阶段 B 代码和阶段 C 的
> `RobotTransport + PointRegistry` 已完成；硬件验收仍未执行。86 点当前为 1 个
> `validated`、81 个 `unreviewed`、4 个 `placeholder`，重复位姿组为
> `P6/P24/P41/P42`、`P64/P65`、`P73/P74`。

## 1. 目标与边界

当前机器人 MVP 已跑通上位机 Modbus 读写和 `home`。下一阶段不应直接进入 FastAPI 路由堆叠，而应先把现有机器人程序中的三个基础能力收敛出来：

1. 可追溯、可校验的命名点表。
2. `MoveJ / MoveL` 运动原语。
3. 具有业务语义和到位反馈的末端工具动作。

完成后，上位机可以用“命名点 + 运动方式 + 工具动作”复刻现有机器人程序中的大部分固定取放流程。原机器人程序继续保留为事实来源、现场 fallback 和迁移对照，不立即删除。

生产路径不直接开放任意裸坐标和任意 DO 写入。裸坐标运动、裸 IO 仅用于受控维护/标定模式；生产编排优先使用已验收命名点和语义工具动作。

## 2. 当前点表事实

当前来源文件：

`机器人程序/机器人程序v0.11/roboprogram/point.json`

文件现有 86 条记录，每条已经包含：

- `id`：UUID，可作为导入来源标识。
- `name`：机器人程序名，例如 `P1`。
- `alias`：点位语义名称，例如 `Home`、`Area_1_Ready`。
- `pose`：`[x, y, z, rx, ry, rz]`。
- `joint`：`[j1, j2, j3, j4, j5, j6]`。
- `tool`、`user`：工具与用户坐标系编号。

该结构可以作为上位机点位注册表的导入源，但不能未经整理就直接成为生产权威数据：

- `P6/P24/P41/P42` 使用相同的 `[0, -246, 1047, -90, 0, 180]`、`tool=0` 和全零 joint，属于疑似占位或未完成标定点，必须现场确认。
- `P64/P65` 位姿完全相同但 alias 不同；`P73/P74` 也完全相同。需要确认是有意复用、临时复制，还是应合并。
- `Area_n_m` 等 alias 主要表达历史区域编号，不足以让上位机安全编排；需要补充工位、角色和动作语义。
- 点位与旧 Lua 中的相对偏移、接近方向、速度参数存在隐含耦合，整理时不能只看 JSON。

## 3. 上位机点位模型

建议保留原始字段，并在上位机侧增加规范化元数据：

```json
{
  "point_id": "robot-main.home",
  "source_id": "7f9ccab2-4010-4444-ba4a-e693a47a36aa",
  "robot_name": "P1",
  "alias": "Home",
  "workstation": "global",
  "role": "home",
  "pose": [-4.64, 107.46, 425.18, 179.41, -0.65, 170.60],
  "joint": [-154.52, -47.78, 93.29, 44.64, -89.06, 125.00],
  "user": 0,
  "tool": 1,
  "allowed_motion": ["move_j"],
  "status": "validated",
  "source_file": "机器人程序/机器人程序v0.11/roboprogram/point.json",
  "source_version": "v0.11",
  "calibrated_at": null,
  "notes": ""
}
```

最低需要新增：

- 稳定的业务 `point_id`，避免流程直接依赖 `Pxx`。
- `workstation`、`role`：区分 ready、approach、target、retreat、home、calibration。
- `allowed_motion`：明确该点允许 `MoveJ`、`MoveL` 或两者。
- `status`：`unreviewed / validated / deprecated / placeholder`。
- 来源文件、版本或校验值、标定时间和备注。

原始 `point.json` 作为导入源和机器人侧事实，不由运行中的 FastAPI 直接修改。上位机先导入为规范化点位注册表；点位变更必须经过标定、校验、版本记录和重新发布。

## 4. 末端 IO 当前事实

旧机器人程序中可确认的主要末端输出为：

| IO | 当前程序语义 | 现状与风险 |
| --- | --- | --- |
| `DO1` | 快换吸气/放气、锁紧/释放 | `Kh_vac()` 使用，具体正负逻辑需现场确认 |
| `DO3` | 吸盘吸气/放气 | `Xp_vac()` 使用，具体正负逻辑需现场确认 |
| `DO2 + DO6` | 夹爪/气缸组合控制 | `Jz_vac()` 及业务路径中存在固定时序；旧代码含“存疑”注释，必须专项验收 |
| `DI1 / DI2` | 夹爪或气缸两端到位反馈 | 旧流程分别等待 DI1、DI2；准确物理含义和 ON 极性需现场确认 |
| `DO5/DO7/DO8` | 初始化时置 OFF | 当前文档无法确认用途，不纳入首批生产 API |

首批生产接口不建议提供通用 `set_do(channel, value)`，而应提供语义动作：

- `tool.quick_change.lock / release`
- `tool.suction.on / off`
- `tool.gripper.open / close`
- `tool.get_state`

每个语义动作必须定义：输出时序、等待的 DI、超时、成功状态、错误码、当前物理状态和是否允许重试。若无可靠传感器反馈，应明确返回 `commanded_state`，不能伪装成已确认 `actual_state`。

裸 `read_di` / `set_do` 仅保留给维护诊断模式，并受通道白名单、权限和审计限制。

## 5. 运动与工具原子动作范围

机器人 MVP 从当前三个动作扩展为：

| 动作 | 用途 |
| --- | --- |
| `query` | 读取机器人状态、pose、joint 和当前工具状态 |
| `home` | 回已验收待命点 |
| `move_j` | 关节运动，主要用于 home、ready 和跨区域转移 |
| `move_l` | 直线运动，主要用于 approach、target 和 retreat |
| `tool_action` | 执行快换、吸盘、夹爪等白名单语义动作 |

`MoveL` 可复用当前目标 pose、user、tool、acc、vel、cp 参数，但需要独立 FunctionID、预检查/错误码和验收记录。若控制器没有可靠的 `CheckMovL` 等价能力，首版只允许从已知起点到已验收终点的命名运动段，不开放任意 `MoveL`。

## 6. 流程编排方式

上位机不直接把旧 Lua 函数整体照搬，而是逐步转换为可读动作模板。例如：

```text
move_j("area_1.ready")
move_l("area_1.approach")
move_l("area_1.target")
tool_action("suction.on")
move_l("area_1.approach")
move_j("home")
```

相对偏移路径可以在第二阶段建模为受限模板，例如 `approach(point, axis="z", offsets=[100, 20])`。首批优先复刻旧程序中已有且经过现场验证的路径，不允许客户中控自由拼接未经验证的碰撞敏感路径。

## 7. 实施顺序

### 阶段 A：冻结事实与整理清单

1. 导入并检查 86 个点，建立 `Pxx -> alias -> 工位 -> 角色 -> 旧 Lua 使用位置` 对照表。
2. 标记疑似占位点、重复位姿、未使用点和坐标系异常。
3. 现场确认 `DO1/DO2/DO3/DO6`、`DI1/DI2` 的接线、极性、机械动作和安全状态；查明 `DO5/DO7/DO8`。
4. 冻结首批验收用的 home、ready、approach、target、retreat 点和安全测试路径。

### 阶段 B：扩展机器人原子协议

1. 保留并复验 `query / home / move_j`。
2. 增加 `move_l`。
3. 增加白名单 `tool_action` 与工具状态反馈。
4. 为运动和 IO 补齐 Busy/Done/Error、超时、错误复位和反馈寄存器。

### 阶段 C：上位机基础层

1. 将测试脚本整理为 `RobotTransport` 接口与 `ModbusRobotTransport` 实现。
2. 实现只读点表导入器和 `PointRegistry`；明确版本、校验和启动自检。
3. 建立机器人单写入者、动作串行锁、模式门控和动作日志。

### 阶段 D：硬件验收

1. 验收 `query / home / move_j / move_l` 的正常、拒绝、超时、断线和复位路径。
2. 逐个验收快换、吸盘和夹爪的命令、反馈、超时及断电/急停后的安全状态。
3. 用命名点复刻至少一条“ready -> approach -> target -> 工具动作 -> retreat”完整取放路径。

### 阶段 E：FastAPI 与流程模板

1. FastAPI 只依赖 `RobotTransport`、`PointRegistry` 和动作服务，不直接操作寄存器或 JSON 文件。
2. 首批开放点表只读查询、命名点运动、受限 `MoveJ/MoveL`、工具语义动作和动作状态查询。
3. 在验收通过后逐步把旧 Lua 固定流程迁移为上位机业务动作模板。

## 8. 完成标准

- 点表中每个生产点都有明确业务 ID、工位、角色、坐标系、工具号、状态和来源版本。
- 占位点与重复点均有处置结论，不会被生产流程误调用。
- 末端工具 IO 映射、极性、反馈和超时均经现场确认。
- 上位机可使用命名点完成受限 `MoveJ/MoveL`，并调用快换、吸盘和夹爪语义动作。
- 同一时刻只有一个上位机动作所有者可以写机器人寄存器。
- 至少一条旧机器人固定取放路径已由上位机编排复刻并完成现场验收。
