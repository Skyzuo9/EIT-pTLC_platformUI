# pTLC 与 Uni-LabOS 接入阶段说明

> 状态说明：本文记录的是此前“渐进式接入 Uni-LabOS”的阶段性方案。2026-06 与客户讨论后，近期需求重点可能从“黑盒 Workstation 接入”调整为“面向客户中控系统开放受控原子动作 API，尤其是机器人动作 API”。本文保留为历史设计依据，新的需求边界见《客户中控原子动作接入需求草案.md》和《pTLC客户对齐简要说明.md》。

> 本文是当前讨论的阶段性说明，用于概述现有项目组织、接入目标变化和短期实施计划。后续方案可能继续调整，因此这里只保留高层边界和推进顺序。

## 1. 当前项目组织结构

当前 pTLC 项目由上位机、PLC、机器人程序和若干辅助模块组成。

```text
pTLC_platform/EIT_Project
├─ UI-Upper/                 # Python 上位机
│  ├─ main.py                # 启动入口，支持 UI / collect / stress 等模式
│  ├─ core/                  # 调度、PLC 通信、阶段执行、视觉、耗材、数据库等核心逻辑
│  │  ├─ scheduler.py        # 样品队列调度器
│  │  ├─ task.py             # RecipeTask 多阶段流程
│  │  ├─ plc_client.py       # OPC UA 客户端与 PLC 变量读写
│  │  ├─ stages/             # spotting / before_photo / develop / scrape / collect
│  │  ├─ vision_service.py   # TLC 图像分析
│  │  ├─ camera_service.py   # 相机抽象
│  │  ├─ cnc_path_generator.py
│  │  ├─ consumable_manager.py
│  │  ├─ resource_manager.py
│  │  └─ sample_store.py
│  └─ ui/                    # NiceGUI 界面
├─ PLCsoftware/              # PLC 工程、变量表和导出文件
├─ 机器人程序/               # 机器人点位、Modbus 协议和 Lua 程序
├─ unilab/Uni-Lab-OS/        # Uni-LabOS 源码
├─ unilabos迁移/             # 接入讨论和迁移计划文档
├─ docs/                     # PLC、阶段协议、调试和设计文档
└─ 液位检测模块/             # OrangePi + MQTT 液位检测模块
```

当前运行边界大致为：

```text
上位机：样品队列、配方、视觉、耗材账本、展缸资源、UI 调试
PLC：工位 FSM、安全互锁、泵/阀/气缸/机器人/CNC 的确定性执行
机器人：通过 ModbusTCP 接收 PLC 的 FunctionID 与参数，执行取放业务动作
Uni-LabOS：尚未正式接入，当前作为未来实验协议、资源模型和跨设备调度层
```

## 2. 当前讨论形成的目标变化

最初的 Uni-LabOS 接入思路偏保守：将现有 pTLC 系统作为一个黑盒工作站接入 Uni-LabOS，由 Uni-LabOS 调用上位机已有能力，而不改动 PLC 和机器人主流程。

后续讨论中，用户提出系统需要更强的调试和使用柔性：自动化实验室中耗材、夹具、点位会频繁变化，运行过程中也会积累误差。因此上位机不应只做高层调度，还需要承担更多点位校准、坐标计算、参数下发和动作编排职责。

新的长期目标可以概括为：

```text
Uni-LabOS / 上位机：实验语义、资源模型、校准、坐标转换、动作编排
PLC：动作准入、安全互锁、I/O 闭环、原子动作执行
机器人：参数化运动或取放动作执行
```

设计原则是：

```text
上位机判断动作“该不该执行”
PLC 判断动作“能不能安全执行”
```

例如，上位机可以根据配方、资源锁、样品状态和校准结果决定是否执行点样动作，并计算点位 XY；PLC 在收到动作请求后，仍需要检查急停、安全门、气压、限位、工位占用、轴状态和参数范围，只有安全条件满足才执行。

## 3. 预期改动方向

### 3.1 上位机

上位机需要逐步从当前的 stage 调度器，扩展为本地动作编排器。

短期应增加：

- 面向 Uni-LabOS 的 pTLC Workstation API。
- 样品入队、状态查询、取消、结果查询、资源状态查询接口。
- 校准数据、点位参数和动作参数的统一管理。
- 业务状态、动作状态和 PLC 拒绝原因的结构化输出。

中长期可能增加：

- 动作模板和 primitive plan。
- 坐标系/校准版本管理。
- 上样针、泵、相机、机器人动作的参数化编排。
- Uni-LabOS protocol 到 pTLC 动作计划的转换层。

### 3.2 PLC

PLC 不应被完全弱化为透明转发层。即使动作由上位机编排，PLC 仍要保留安全裁决权。

预期改动方向：

- 保留现有 stage FSM，作为生产路径和 fallback。
- 增加可观测状态：动作状态、拒绝原因、机器人选择、关键工位状态。
- 后续增加 primitive 动作接口，例如动作 ID、参数数组、请求序号、Ack、Busy、Done、RejectCode、ErrorCode。
- 对每类 primitive 做本地准入检查和参数范围检查。

PLC 不需要把所有内部传感器都开放给上位机作为业务判断依据，但需要开放足够的状态快照和拒绝原因。安全互锁仍应由 PLC 本地闭环判断。

### 3.3 机器人

第一阶段机器人程序可以不改，继续由 PLC 通过 ModbusTCP 下发 `FunctionID` 和参数。

后续若要支持更高柔性，应逐步从固定业务流程扩展为参数化动作库，例如：

- 移动到命名点位。
- 带坐标参数的安全 MovJ / MovL。
- 参数化取放板、取放收集器、取放收集瓶。
- 工具、吸盘、夹爪等末端动作反馈。

不建议一开始直接开放裸 `MovJ` 给上位机无约束调用。更合适的是开放带安全边界和参数校验的业务原子动作。

## 4. 当前简短实施计划

### 阶段 1：黑盒工作站接入

目标是让 Uni-LabOS 能调用当前 pTLC 系统，而不改变现有生产流程。

- 新增 pTLC Workstation API。
- 暴露启动样品、查询状态、取消任务、查询结果等接口。
- Uni-LabOS 先把 pTLC 作为一个设备/工作站使用。

### 阶段 2：状态观测与资源镜像

目标是让 Uni-LabOS 和上位机看到更完整的运行状态。

- 输出样品、stage、展缸、耗材、机器人、E-Stop、视觉等待状态。
- 整理资源模型：样品、硅胶板、展缸、收集器、收集瓶、耗材槽位。
- 增加机器人实际动作选择和耗时记录。

### 阶段 3：参数上移

目标是先获得调试柔性，而不拆掉 PLC 的 stage FSM。

- 上位机负责计算并下发点位、泵参数、槽位、路径参数。
- PLC 仍执行现有 spotting / develop / scrape / collect 等 FSM。
- 引入校准版本和参数生效记录。

### 阶段 4：primitive 调试接口

目标是在 Debug/Calibration 模式下开放有限原子动作。

- 增加安全门控的点动/移动/泵/阀/相机接口。
- 生产任务运行中禁止普通 primitive 调试动作。
- PLC 返回明确的 `REJECTED / BUSY / UNSAFE / DONE / ERROR` 状态。

### 阶段 5：局部动作编排上移

目标是选择低风险模块先做 stage 内部编排上移。

优先考虑：

- 上样针 XY 点位与泵动作。
- 相机拍照与视觉校准流程。
- 部分耗材取放的参数化动作。

暂不优先拆：

- 完整机器人业务流程。
- 安全互锁。
- 急停和异常恢复主逻辑。

## 5. 当前建议

短期不要直接让 Uni-LabOS 或上位机绕过 PLC 控制机器人和执行器。更稳妥的路线是：

```text
先接入，再观测，再参数上移，再开放受限 primitive，最后局部编排上移
```

这样既保留当前系统已经跑通的生产路径，也能逐步实现自动化实验室所需的高柔性调试能力。
