# 客户中控原子动作接入需求草案

## 1. 背景变化

此前 pTLC 与 Uni-LabOS 的接入思路偏向渐进式迁移：先将现有 pTLC 系统作为黑盒工作站接入，再逐步开放状态观测、资源模型和局部 primitive 调试能力。

2026-06 与客户沟通后，需求重点发生变化。客户实验室已有中控系统，并已接入有机合成工作站、HPLC 工作站等设备。客户更习惯由中控系统下发原子化动作指令，执行单元收到指令后完成安全检查、动作执行、过程反馈和结果反馈。

因此，pTLC 近期接入目标需要从“完整流程黑盒调用优先”调整为“受控原子动作 API 优先”，并保留现有完整 pTLC 程序作为本地运行、调试和 fallback 能力。

## 2. 当前已知需求

- 客户要求我方提供 FastAPI 接口。
- 第一批原子动作仍从机器人 MVP 开始。
- 第一批 MVP 当前考虑采用 pTLC 上位机直连机器人，舍弃 PLC 中间通讯。
- 客户希望点位由 pTLC 上位机维护；上位机向中控提供点表信息和标定程序，便于柔性生产。
- 当前 `机器人程序/机器人程序v0.11/roboprogram/point.json` 可作为上位机点表的首批导入源，但需要先完成语义分类、占位/重复点处置、版本与校验状态整理。
- 第一批机器人原子能力应同时纳入受限 `MovL` 与末端工具 IO，以便上位机复刻旧机器人程序中的接近、取放和退出路径。
- 资源账本由 pTLC 上位机管理，中控通过数据库或 API 查询资源状态。
- 反馈粒度需要扩充，不能只提供 Done/Error。
- `MovJ` 是否受限、限制范围如何定义仍需讨论，尤其涉及碰撞管理时复杂度较高。
- 后续可能由 pTLC 上位机进行流程编排，PLC 和机器人不一定暴露完整流程信息。
- PLC 侧 stage FSM 内部动作后续仍可能拆解为更细粒度的工位动作或执行器动作，例如拍照、遮光气缸开关、展缸盖开关、伺服移动等，但第一批暂未要求。
- 现有 pTLC 上位机、PLC FSM、机器人程序和 NiceGUI UI 倾向继续保留。

## 3. 新的总体边界

建议采用以下职责划分：

```text
客户中控：实验流程编排、跨工作站调度、业务动作二次封装、查询资源/结果
pTLC 上位机：FastAPI 入口、机器人直连、点位/标定管理、资源账本、状态聚合、日志记录、兼容现有任务队列和后续流程编排
PLC：保留现有工位 FSM、安全互锁和 I/O 闭环；第一批机器人 MVP 不经 PLC 中转
机器人：执行 pTLC 上位机直连下发的查询、移动和回原点等动作
```

核心原则：

```text
中控决定实验意图和跨工作站编排
pTLC 上位机负责点位、资源、动作封装和流程编排
PLC 在涉及工位硬件时仍负责安全互锁和 I/O 闭环
机器人负责执行上位机授权后的运动
```

## 4. API 粒度建议

原子动作 API 不建议只有一种粒度，建议分为三层。

### 4.1 设备原子动作

面向最底层设备能力，例如：

- 机器人受限 `MovJ`
- 机器人受限 `MovL`
- 读取机器人当前位置
- 通过白名单语义动作切换快换、吸盘、夹爪等末端执行器状态
- 伺服移动到指定位置
- 气缸打开/关闭
- 展缸盖打开/关闭
- 泵吸液/排液
- 阀切换
- 相机拍照
- CNC 移动

这层灵活性最高，但风险最大。建议仅在明确模式门控、参数范围检查、区域限制、互锁检查后开放。

### 4.2 业务原子动作

面向客户更容易二次封装和理解的动作，例如：

- 移动到命名安全点
- 取硅胶板
- 放硅胶板到指定工位
- 取/放收集器
- 取/放收集瓶
- 换工具
- 拍照，内部包含伺服移动、遮光气缸、相机触发和回位
- 打开或关闭指定展缸
- 单次点样

这层建议作为生产接入的主要能力，因为它保留业务语义，也更方便 PLC 和上位机做前置条件检查。

### 4.3 工作站流程动作

保留现有 pTLC 流程能力，例如：

- 启动完整 pTLC 配方
- 启动某个 stage
- 查询样品状态
- 取消样品
- 查询样品结果

这层用于兼容当前系统，也可作为客户中控不需要细粒度编排时的高级接口。

## 5. 第一批建议聚焦：机器人动作 API

客户明确希望上位机掌控机器人点位信息，并在业务动作时下发点位。第一批围绕机器人动作做 FastAPI 和上位机直连封装设计。

候选动作：

- `robot.get_status`
- `robot.get_pose`
- `robot.move_j`
- `robot.move_l`
- `robot.move_to_named_point`
- `robot.home`
- `robot.tool_action`

其中 `move_j` 是否必须做成受限 `MovJ` 仍需讨论。建议至少包含：

- 请求序号 `request_id`
- 坐标系 `frame`
- 目标位姿 `pose`
- 速度/加速度上限
- 工具号或末端状态
- 允许区域或动作场景，若第一批无法完成碰撞管理，可先采用轻量限制
- 超时时间
- 调用方标识
- 是否回原点 `return_home`，由上位机流程编排决定，不作为底层动作默认行为

上位机或机器人控制侧需要检查：

- 急停、安全门、气压、限位等安全状态
- 当前是否存在 pTLC 自动任务或上位机流程占用
- 当前机器人是否 Busy
- 当前工位或资源账本是否允许该动作进入
- 目标点是否在允许区域内，后续再评估完整碰撞模型
- 速度、加速度、姿态是否在限制范围内
- 末端工具状态是否满足动作要求

现阶段生产接口不直接开放任意 `set_do`。旧程序中的 `DO1`（快换）、`DO3`（吸盘）、`DO2 + DO6`（夹爪组合时序）以及 `DI1/DI2` 到位反馈需先完成现场确认，再映射为 `lock/release`、`on/off`、`open/close` 等语义动作。裸 IO 只允许在维护模式使用。

## 6. PLC 工位动作拆解讨论

除了机器人动作，PLC 侧 stage 内部动作后续也可能需要开放给上位机或客户中控做二次封装。本次客户暂未要求第一阶段开放，但建议保留三层讨论框架。

近期内部探索目标：先以 collect 收集工位作为第一个 PLC 工位动作拆解样例。原因是 collect 相对简单，没有视觉确认和 CNC 路径生成，主要由收集平台气缸、收集泵/阀、机器人交接、地轨伺服到站和耗材账本组成，适合作为动作结构划分的试验场。

本轮目标不是直接把 collect 的每个 IO 都开放成外部 API，而是先完成：

- 梳理 collect 当前 PLC FSM：`Collect_Init -> Collect_LoadPowderCollector -> Collect_LoadBottle -> Collect_Elute -> Collect_UnloadBottle -> Collect_UnloadPowderCollector`。
- 建立动作分层：执行器原子层、工位动作层、业务编排层。
- 明确哪些动作适合复用底层 FB，例如气缸 `FB_cylinder`；哪些动作必须保留工艺语义，例如地轨到站后机器人取放。
- 补齐动作反馈：动作当前 step、Busy、Done、Error、ErrorCode、timeout、关键传感器状态。
- 暂时保留现有完整 `collect_Enable` 调用作为生产主路径，避免过早把安全互锁上移到客户中控。

可用于推进执行的简短 prompt：

```text
从第一性原理出发推进 collect 工位动作拆解：PLC 负责原始传感器、I/O 闭环、安全互锁、动作执行和可重试性判断；上位机只表达动作意图并消费动作状态、结果、错误码、诊断摘要和 retryable/safe_state。不要把所有传感器直接上移给上位机，也不要让上位机盲目重试非幂等物理动作。先在不破坏现有 collect_Enable 完整流程的前提下，梳理 Collect_Init、Collect_LoadPowderCollector、Collect_LoadBottle、Collect_Elute、Collect_UnloadBottle、Collect_UnloadPowderCollector 六个工位动作，明确每个动作的入口条件、完成条件、失败条件、执行器依赖、物理状态变化、错误码、恢复方式和是否可自动重试。
```

collect 样例中需要特别注意伺服：虽然收集平台本体主要是气缸/泵/阀，但机器人取放收集瓶和粉末收集器前依赖地轨 `地轨轴11YDATE` 到收集、暂存、仓库等点位。因此伺服动作应作为独立类别纳入原子化模型，不能只把“运动原子”粗略写成机器人动作。

### 6.1 大粒度工位动作

这类动作保留完整业务语义，由 PLC 或上位机负责内部时序。

例如“拍照”动作可以包含：

```text
伺服移动到拍照位置 -> 遮光气缸关闭 -> 触发相机拍照 -> 遮光气缸打开 -> 伺服回位
```

其中拍照位置、是否回位、曝光配置、超时时间等可以作为参数。

### 6.2 小粒度执行器动作

这类动作更接近具体执行器，例如：

- 伺服移动到指定坐标
- 遮光气缸关闭
- 遮光气缸打开
- 打开展缸盖
- 关闭展缸盖
- 单个泵/阀动作
- 读取某个传感器或到位信号

小粒度动作柔性更高，但客户中控需要承担更多动作顺序、互锁状态、异常恢复和资源一致性责任。

伺服动作建议单独分层，不与气缸混在同一抽象里：

- 裸轴动作：`AxisHome`、`AxisMoveAbs`、`AxisMoveRel`、`AxisStop`、`AxisResetError`、`AxisWaitInPosition`。
- 安全运动模板：`MoveRailToStation`、`MoveZThenXYThenZ`、`MoveXY`。这类动作封装软限位、速度/加速度限制、避碰顺序和到位超时。
- 工艺运动段：拍照轴准备、点样针移动、刮板路径执行、地轨配合机器人到站。

生产 API 优先暴露安全运动模板或工艺运动段；裸轴动作仅建议用于维护、标定、调试模式。

### 6.3 只读状态动作

只读状态可优先开放，风险较低，例如：

- 工位占用状态
- 气缸到位状态
- 展缸盖开闭状态
- 伺服当前位置
- 相机就绪状态
- PLC 当前模式与错误码

### 6.4 建议

建议不要一次性把 PLC 内部所有 BOOL 都暴露为外部 API。更稳妥的做法是先列出客户希望编排的业务动作，再判断每个动作应该暴露为大粒度工位动作、小粒度执行器动作，还是只读状态。

### 6.5 传感器与重试边界

上位机不需要、也不应在生产编排中掌握所有原始传感器。更合理的边界是：

```text
PLC 掌握原始传感器、互锁条件、硬件闭环和安全判断。
上位机掌握动作意图、动作生命周期、结果、错误码、诊断摘要、可重试性和恢复建议。
```

传感器可作为维护/诊断只读信息暴露，但不应成为上位机生产编排的主要判断依据。上位机关心的是动作是否完成；若失败，关心失败大类、错误码、当前安全状态和是否允许重试。

重试策略必须由 PLC 或动作层明确给出 `retryable`，不能由上位机根据超时自行猜测。建议默认规则：

- 可自动重试：通信查询、泵状态查询、等待空闲、只读状态刷新等不改变物理世界的动作。
- 谨慎重试：泵进液、排液、正压排液等流体动作，必须确认不会重复加液或重复排液后才允许。
- 默认不可盲重试：机器人取放、气缸夹持、收集瓶/粉末收集器交接、地轨到站后联动动作。这些动作具有非幂等物理效果，重复下发可能造成位置、夹持和账本不一致。

动作结果建议包含：

```json
{
  "status": "DONE | ERROR | TIMEOUT",
  "step": 70,
  "error_code": "BOTTLE_NOT_DETECTED",
  "message": "收集瓶未检测到",
  "retryable": false,
  "safe_state": "WAITING_RECOVERY"
}
```

这个边界保留 PLC 的安全闭环责任，也让上位机可以用简洁稳定的动作语义做编排。

## 7. 动作状态与反馈建议

每个动作建议采用统一生命周期：

```text
SUBMITTED -> ACCEPTED / REJECTED
ACCEPTED -> RUNNING
RUNNING -> DONE / ERROR / CANCELLED / TIMEOUT
```

建议统一返回字段：

- `request_id`
- `action_id`
- `status`
- `accepted`
- `reject_code`
- `error_code`
- `message`
- `step`
- `progress`
- `started_at`
- `updated_at`
- `finished_at`
- `result`

拒绝原因建议结构化，例如：

- `BUSY`
- `ESTOP_ACTIVE`
- `UNSAFE`
- `INVALID_PARAM`
- `OUT_OF_RANGE`
- `WORKSTATION_OCCUPIED`
- `MODE_NOT_ALLOWED`
- `RESOURCE_CONFLICT`
- `PLC_NOT_READY`

## 8. 模式门控建议

为了保留现有生产路径并降低风险，建议引入外部控制模式：

```text
LOCAL_AUTO：现有 pTLC 自动流程，默认模式
LOCAL_MANUAL：本地调试/恢复
EXTERNAL_CONTROL：客户中控原子动作控制
MAINTENANCE：维护/校准
```

初期建议：

- `LOCAL_AUTO` 中不允许客户中控下发普通机器人移动指令。
- `EXTERNAL_CONTROL` 中允许机器人直连动作，但必须确认没有本地自动任务或上位机流程冲突。
- 本地 UI 保留模式切换、急停状态、动作日志和恢复入口。
- 涉及 PLC 工位硬件时，PLC 仍保留安全互锁和拒绝权。

## 9. 资源状态待确认

资源状态是本次对齐的关键未决项。需要明确以下资源的权威维护方：

- 样品
- 硅胶板
- 展开缸
- 拍照/刮板工位
- 收集工位
- 粉末收集器
- 收集瓶
- 耗材架槽位
- 机器人工具状态

当前结论：

- 资源账本由 pTLC 上位机维护。
- 中控通过数据库或 API 查询资源、样品、动作日志和结果。
- 中控不直接绕过上位机修改资源状态。
- 动作完成后的状态同步规则和异常回滚规则仍需在数据库/API 设计中明确。

## 10. 与旧 Uni-LabOS 迁移方案的关系

旧方案仍有价值，但优先级需要调整：

```text
旧主线：
黑盒 Workstation -> 状态观测 -> 参数上移 -> primitive -> 局部编排上移

上一轮主线：
状态/资源建模 -> 机器人原子动作协议 -> 安全准入与反馈 -> 客户中控编排接入 -> 保留完整 pTLC 流程作为兼容能力

当前主线：
FastAPI 接入 -> 上位机直连机器人 MVP -> 上位机维护点位/标定/资源账本 -> 扩充动作反馈 -> 后续由上位机逐步编排 PLC 与机器人流程
```

换句话说，完整 pTLC 流程接口仍保留，但不再是唯一接入入口。第一批先用 FastAPI 机器人 MVP 建立闭环，再逐步扩展上位机流程编排和 PLC 工位动作能力。

## 11. 待客户确认问题

1. `MovJ` 限制范围如何定义：只做参数范围、命名区域、资源占用检查，还是需要完整碰撞管理？
2. 上位机直连机器人采用哪种底层接口：复用当前机器人 Lua/Modbus 寄存器方案，还是改用更直接的机器人控制接口？
3. 点表和标定程序需要向中控开放到什么粒度：只读点表、标定任务、点位编辑、版本管理？
4. 中控查询数据库的方式是直接读数据库、通过 FastAPI 查询，还是两者都支持？
5. 外部动作是否允许在 pTLC 自动队列运行中插入，还是必须由上位机统一编排并做模式互斥？
6. 后续 PLC 工位动作优先拆哪一类：拍照、展缸、泵阀、气缸、CNC，还是只读状态？
7. 动作反馈需要包含哪些字段：step、pose、joint、资源状态、互锁状态、错误码、日志、操作员身份？
8. 是否需要权限分级、审计日志和动作回放？
9. 后续是否由上位机承担完整流程编排，客户中控只调用业务动作和查询结果？
10. 第一批 FastAPI MVP 的交付范围、现场验证动作和责任人需要补充确认。
