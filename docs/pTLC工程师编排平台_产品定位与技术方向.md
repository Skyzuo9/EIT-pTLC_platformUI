# pTLC 工程师编排平台：下一阶段开发重点

> 本文只回答三个问题：下一阶段做什么、设备节点怎么划分、做到什么程度算完成。

## 1. 一句话结论

下一阶段只做一条主线：

> 建立“资源感知的多工作流调度”，让多个样品在资源不冲突时真正并行，在争用 PLC 工位、机器人、泵、槽位或机械空间时自动排队，并让等待原因和设备状态可见。

当前最缺的不是 `parallel` 语法，也不是更多流程编辑功能，而是一个能判断“这个动作现在能不能安全启动”的 Scheduler。

设备节点是 Scheduler 下发动作和确认状态的执行边界。它不是线程，也不要求“一台物理设备一个节点”。

## 2. 当前能力与核心缺口

| 已有能力 | 现状 | 结论 |
|---|---|---|
| PLC 控制与动作协议 | 已有 RequestSeq、状态、步骤、错误码、安全状态和断线对账约定 | 保留，不重写 |
| 动作执行 | `ActionExecutor` 已能调用 PLC、机器人、相机和视觉动作 | 保留 |
| 单工作流 | mini-VM 已支持顺序、条件、循环、子流程和人工节点 | 已基本具备 |
| 工作流内并行 | `_op_parallel` 能创建 asyncio Task，并支持 `join: all/any` | 只有并发原语，不是完整调度 |
| 资源互斥 | `ResourceGate` 只有进程内字符串锁 | 缺少所有者、等待原因、租约生命周期和故障对账 |
| 多样品调度 | 当前活动的 `eit_ptlc` runtime 未接入样品队列和资源调度器；`VmController` 只有适配入口和无准入控制的并发 Task | 下一阶段的核心缺口 |
| 设备节点 | `NodeRegistry` 目前主要提供状态快照和健康监控 | 缺少统一执行、取消和对账接口 |

还需要特别修正两个问题：

1. 当前活动工作流还没有实际使用 `parallel`，现有测试也没有证明真实重叠、资源冲突、取消传播和设备断线行为。
2. 当前并行分支共享同一个运行 Frame；分支同时写变量会产生不确定结果。各分支必须使用独立作用域，输出只能按显式规则合并。
3. `join: any` 取消 Python Task，不代表 PLC 或机器人已经停止。所有可能遗留的物理分支都必须具备可验证的取消协议，否则保存或启动时拒绝该流程。

并行有三个层级，不应混在一起：

| 层级 | 谁负责 |
|---|---|
| PLC 内部实时并行、互锁和急停 | PLC L1 |
| 一个工作流中的并行分支 | mini-VM 表达，Scheduler 执行 |
| 多个样品、多个工作流同时运行 | Scheduler 统一调度 |

下一阶段重点是第三层，并把第二层接入同一套资源规则。

## 3. 下一阶段要实现的闭环

```text
mini-VM 产生待执行动作
        ↓
Scheduler 读取动作所需节点和资源
        ↓
原子取得全部资源租约，否则进入 WAITING_RESOURCE
        ↓
确认目标 Device Node 健康并下发动作
        ↓
取得物理终态，或进入下一阶段新增的 OUTCOME_UNKNOWN 等待对账
        ↓
安全释放资源，唤醒后续动作
```

需要完成五项改动。

### 3.1 扩展动作契约

每个可编排动作至少声明：

```yaml
sampling.aspirate:
  target_node: plc-main
  capability: sampling.aspirate
  resources:
    - station:sampling
    - pump:sampling
  timeout_s: 120
  idempotent: false
  cancellable: false
```

资源首先只覆盖真正会阻止并行的对象：PLC 工位、独立设备、共享总线、槽位和机械空间。

### 3.2 实现 Scheduler 和资源租约

Scheduler 必须做到：

- 多个 Workflow Run 可以同时进入系统。
- 一次性取得动作所需的全部资源，不能持有一半资源继续等待。
- 每个租约记录 `run_id`、`action_id`、资源、取得时间和释放条件。
- 冲突动作进入 `WAITING_RESOURCE`，并记录具体等待对象。
- 节点离线时不下发新动作。
- 只有物理终态明确或完成对账后才释放资源。
- 新增正式的 `OUTCOME_UNKNOWN` 动作状态，并写入运行记录和界面；已受理动作断线时不得盲目重试。

### 3.3 建立最小 Device Node 接口

下一阶段只需要以下接口：

```text
describe()    返回节点版本与能力
health()      返回 online、offline、degraded 或 fault
execute()     执行动作
cancel()      在动作允许时请求安全取消
reconcile()   断线恢复后确认已受理动作的真实结果
```

忙闲属于 capability 或 Resource/Lease，不属于整个节点的健康状态；只有节点整体容量确实为 1 时才能整体互斥。

`NodeRegistry` 从只读监控表扩展为节点实例和状态索引。`ActionExecutor` 作为普通动作的统一入口，负责契约和参数校验并把 Action Request 提交给 Scheduler；Scheduler 获得资源后通过节点接口执行具体能力。

### 3.4 让所有普通动作统一走 Scheduler

工作流、维护界面和直接 API 都不能绕过资源准入，固定调用链如下：

```text
mini-VM / 维护 UI / API
        → ActionExecutor 校验契约和参数
        → Scheduler 申请资源
        → Device Node 执行动作
```

急停和安全停止不等待普通资源租约，走独立的高优先级安全通道，并最终由 PLC L1 或独立安全系统执行。工作流内 `parallel` 和多工作流运行共用同一个 Scheduler，避免两套并发规则。

并行分支必须各自持有局部 Frame；分支结果通过预先定义的字段映射合并，禁止同时隐式写入同一变量。

### 3.5 补齐最小可观测界面

时间线只需先显示：

- 哪个 Workflow Run 和 Action 正在运行。
- 正在等待哪个资源或哪个离线节点。
- 动作实际开始、结束和重叠时间。
- 节点、资源租约以及 PLC RequestSeq 的关联关系。

这不是一次完整 UI 重构，而是让工程师能够解释调度结果。

## 4. 设备节点怎么划分

定义：

> 一个独立通信连接、命令串行化规则和故障恢复边界，对应一个 Device Node。

最重要的判断是：

> 节点粒度不决定并行粒度，资源粒度才决定并行粒度。

例如 Sampling 和 Develop 可以属于同一个 `plc-main` 节点；只要动作申请不同工位资源，它们仍然可以并行。反过来，机器人和 PLC 虽是不同节点，如果共同占用 `zone:robot-transfer`，也必须互斥。

建议映射如下：

| 现场对象 | 控制层建模 |
|---|---|
| 一台主 PLC 及其工位、EtherCAT 轴、泵、阀和 IO | 一个 `plc-main` 节点；工位和可并行单元建模为 capability/resource |
| 一台独立机器人控制器 | 一个 `robot-main` 节点 |
| 一个独立相机 SDK 或服务 | 一个 Camera Node |
| 一台远程液位检测工控机 | 一个 WaterLevel Node |
| 多个设备共用一条串口或 CAN 网关 | 一个 Gateway Node；各设备建模为 capability/resource |

EtherCAT 从站、阀和 IO 继续由 PLC L1 管理，不应拆成上位机节点。

第一阶段保持单个后端进程：

- 每个 Workflow Run 使用一个 asyncio Task。
- 每个并行分支使用一个 asyncio Task。
- 每个 Device Node 是持有长连接和状态的长期对象。
- 阻塞式 SDK 才放入线程池。
- 只有远程主机、独立重启或 SDK 崩溃隔离确有需要时，节点才拆成独立进程。

因此，不采用“一台设备一个线程”或“一台设备一个 Python 进程”的固定规则。

## 5. 唯一验收场景

用两个样品验证完整闭环：

```text
样品 A：点样 ── 机器人转运 ── 槽位 1 长时处理 ── 机器人取回
样品 B：                         点样 ── 等待机器人 ── 槽位 2 处理
```

必须同时满足：

1. A 在槽位 1 处理时，B 能使用已经空闲的点样工位。
2. A 和 B 不能同时占用机器人或同一机械空间。
3. 槽位 1 和槽位 2 可以真实重叠运行；事件时间戳能证明存在重叠。
4. 资源释放后，等待动作能被自动唤醒；界面显示具体等待原因。
5. Robot Node 离线时不再下发新的机器人动作。
6. PLC 已受理动作后通信断开，PLC 继续按本地逻辑运行；上位机进入 `OUTCOME_UNKNOWN`，不重试、不提前释放资源，恢复后完成对账。
7. `join: any` 的所有可能遗留物理分支都具备可验证的取消协议；否则流程校验不通过。
8. 所有动作都能追溯到 `run_id`、`action_id`、`command_id`、Device Node 和资源租约；PLC 动作额外关联 RequestSeq。

只有这组场景在仿真和真机上都通过，才能称为具备并行调度能力。

## 6. 本阶段边界

开发顺序就是第 3.1 至 3.5 节；每一步都以前一步的契约为输入，不并行建设另一套执行链。

本阶段明确不做：

- 不重写现有 PLC 控制程序和 L2 动作协议。
- 不新增一套工艺 DSL。
- 不建设消息总线、服务发现或“一设备一进程”的分布式系统。
- 不先做完整物料库存、编辑器重构、AI 审查或 ST 在线编辑。
- 不让 pTLC 替代 PLC IDE。

## 7. 现场工位后续事项

当前各工位的大动作已经基本跑通，后续以现场细节调整和标定为主。这些事项与平台调度主线并行推进，不改变第 3 节的开发方向。

| 工位 | 当前情况 | 后续事项 |
|---|---|---|
| 上样/点样 | 点样参数基本确定 | 更换三通阀；更换后复核阀控制和现有点样参数 |
| 展开 | 液位标定仍在进行 | 完成标定并固定最终参数版本 |
| 刮板 | 实际作业区域与绘制区域略有偏差；对刀程序已编写但尚未实装 | 实装对刀程序，并据此校正刮板作业区域 |
| 收集 | 当前耗材滤芯尺寸需要改进 | 确认并验证新的滤芯尺寸 |

现场调整完成后，按实际影响同步以下工程信息：

- 三通阀涉及的 PLC I/O 或控制逻辑。
- 液位标定参数及其版本。
- 刮板对刀结果、坐标和安全作业区域。
- 滤芯尺寸及对应耗材规格。
- 受到影响的 Action Contract、PLC ST 映射和验收用例。
