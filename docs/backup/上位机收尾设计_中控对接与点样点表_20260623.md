## 0. 关键发现（先读，决定一切落点）

核对运行时装配后，发现**上样存在两条并行编排，且活路径尚未采用 B 方案**：

| 路线 | 文件 | 是否接进运行时 | 上样目标机制 |
|---|---|---|---|
| **A. 操作 VM（活路径）** | [config/operation/03_sampling/sampling_full.yaml](../../eit_ptlc/config/operation/03_sampling/sampling_full.yaml) → [action/executor.py](../../eit_ptlc/action/executor.py) → [plc_controller.execute](../../eit_ptlc/controller/plc_controller.py#L141) | ✅ bootstrap 装 `VmController` | `sampling.aspirate` 传 `source_x/source_y`（整数孔索引，**当前硬编码 `lit:1`**），**旧 coordinate 风格**，未走 `*_Target` |
| **B. RecipeRunner + Scheduler（离线资产）** | [operation/recipe.py](../../eit_ptlc/operation/recipe.py)、[operation/scheduler.py](../../eit_ptlc/operation/scheduler.py) | ❌ 仅测试引用，**未进 bootstrap** | `push_well`→写 `Sampling_4X/3Y_Target`（**B 方案**），复用 L2 DONE 握手 |

**含义**：架构文档 T8 记的「按孔推送已完成」是在路线 B（离线、未接线）里实现的；**真正跑的路线 A 还没接 B 方案**。所以议题①②的本质不是「填个字段」，而是**让活路径（VM）采用 B 方案**。这导出一个必须先拍板的抉择（见 §3）。

> 也没有任何「下单 API」：全工程无 `SampleRequest(...)` 构造点（除测试），`Scheduler` 未实例化。中控对接是一个**尚不存在的入口模块**。

## 1. 议题① — 中控对接 → 按孔上样

### 1.1 现状
- 活路径 [sampling_full.yaml:16](../../eit_ptlc/config/operation/03_sampling/sampling_full.yaml#L16) `sampling.aspirate args:{source_x:lit 1, source_y:lit 1}`——孔位写死。
- 动作定义 [plc_sampling.yaml:33-42](../../eit_ptlc/config/actions/01_sampling/plc_sampling.yaml#L33) `source_x`(列 1-8)/`source_y`(行 1-6) 为整数孔索引。
- 离线路线 B 已有 `push_well(instance, Well(row,col))`→仿射→写 `*_Target`，但未接活路径。

### 1.2 第一性原理（你已确认：1 样品 = 1 孔）
一个样品在上样阶段就是**一个孔**。所以：
- `wells` 语义 = 「该样品占哪一个孔」（退化为单孔，不是真列表）。
- 上位机**不分配孔**——孔由**中控大 JSON 给定**（你确认）。上位机只解析 + 翻译 + 下发。
- `consumable_manager` 至多做**校验/账本记录**，不当分配器。

### 1.3 设计：中控 JSON → 样品 → 按孔下发
```
中控大 JSON ──> [下单 API: /api/orders (新)] ──> 逐样品构造内部请求 ──> 排程/直接执行
                                                          │
                          每样品: plate_instance + 单孔(row,col) + 工艺参数
                                                          │
                       上样吸液前: 仿射翻译(row,col)→(X,Y) → 写 Sampling_4X/3Y_Target
                                   (复用 calibration_service.push_well / plate_affine)
                                                          │
                                   触发 L2 吸液(50) → 复用 DONE 握手
```

**建议的中控 JSON 契约**（待中控对齐；你说格式中控未定，故先给建议，并把上位机解析层做成可适配）：
```jsonc
{
  "batch_id": "B20260623-01",
  "samples": [
    {
      "sample_id": "S001",
      "plate_instance": "rack_A",      // 须对应 calibration.yaml 已标定实例 id
      "well": {"row": 2, "col": 3},     // 或孔号 well_no: 15 (二选一, 见待决①)
      "process": { "sample_volume_ml": 5.0, "...": "工艺参数" }
    }
  ]
}
```
**解析层**（建议在新 `api/order_routes.py` + 一个 `controller/order_intake.py`）：把每个 sample 翻译为活路径可执行的形式（VM 变量注入 或 SampleRequest），孔位表示法（row,col vs 孔号）在此**单点适配**——孔号→(row,col) 复用 [plate_affine](../../eit_ptlc/controller/plate_affine.py) 的孔序定义。

### 1.4 复用既有 B 方案资产
`push_well` / `plate_affine` / `calibration_service` / `plates.yaml` / `calibration.yaml` 已建且离线全绿，**直接复用**，无需重写——只需把它们接到活路径的「吸液前」钩子。

### 1.5 待决
- **D1.1 孔位表示法**：中控用 `(row,col)` 还是 `孔号`？（你：中控未定 → 上位机解析层做成两者皆可，但需中控最终给定其一以定校验）。
- **D1.2 plate_instance 命名**：中控的板实例 id 如何与上位机 `calibration.yaml` 已标定实例对应（同名约定？映射表？）。

## 2. 议题② — 点样/拍照伺服点表

### 2.1 现状
- 活路径 [sampling_full.yaml:19](../../eit_ptlc/config/operation/03_sampling/sampling_full.yaml#L19) `sampling.spot`（动作码 60）**无位置参数**；点样位 6X/7Y 现由 PLC 读 `position[2/3]`，拍照 8Y 读常量 420。
- B 方案后 PLC 改读 `Spot_6X_Start/End`、`Spot_7Y_Target`、`Photo_8Y_Target`（`Host_Computer` flat 节点，**PC 单写者**）——但**上位机目前没有任何地方在运行流程里写这些**（只有点位页 `CalibratePanel` 手动下发）。

### 2.2 存储抉择（对照你问的「现有伺服点位怎么存」）
现状三类存储：

| 类别 | 真值存哪 | 写者 | 持久 |
|---|---|---|---|
| 固定服务位（地轨6位/5Z/清洗位） | **PLC `HMI_Date.position[slot]`** | HMI 示教 | ✅ PLC retain |
| `points.yaml plc_servo` | 只存**绑定**(轴/节点/槽/限位/标签)，不存值 | 点位页经 OPC 读写 PLC 槽 | 配置 |
| 上样仿射目标(4X/3Y) | **PC `calibration.yaml`**(3点标定+解算) | 点位页 CalibratePanel | 配置 |

**抉择推理**：点样/拍照在 B 方案下走 flat 节点，而 **flat 节点不 retain（PLC 重启即丢）** → 真值**必须 PC 侧持久化**，不能像固定位那样靠 HMI 槽。它**非仿射**（直接点表、逐带），故不属 `calibration.yaml`。结论：**新增一类「PC 侧 flat 目标点位」存储**，结构最接近 `points.yaml plc_servo`，但 `node` 指向 `Spot_*Target`/`Photo_8Y_Target` 且**值直接存在配置里**（因 PC 是写者）。

### 2.3 设计：点表结构 + 写者 + 注入点
**存储**（建议扩展 [points.yaml](../../eit_ptlc/config/points.yaml) 增一节，复用其加载/校验/点位页 UI，避免新建散文件）：
```yaml
# points.yaml 新增: PC 侧 flat 目标点位 (值直接存; 区别于 plc_servo 的"只绑定")
plc_servo_target:
  - {key: spot_6x_start, node: Spot_6X_StartTarget, label: 点样6X起点, value: 0.0, limits: {min: -500, max: 500}}
  - {key: spot_6x_end,   node: Spot_6X_EndTarget,   label: 点样6X终点, value: 0.0, limits: {min: -500, max: 500}}
  - {key: spot_7y,       node: Spot_7Y_Target,      label: 点样7Y,    value: 0.0, limits: {min: -500, max: 500}}
  - {key: photo_8y,      node: Photo_8Y_Target,     label: 拍照8Y,    value: 0.0, limits: {min: -500, max: 500}}
```
- **写者**：点位页（PointsView 现有「孔板标定」tab 旁加「点样/拍照点位」编辑；jog 读 `*_ActPos` 微调→存 value）。与现有点位页同源，零新范式。
- **下发**：`points_service` 加 `push_target(key)` → 限位校验 → `write_variable(node, value)`（写 flat 节点，**不是** struct 槽）。
- **注入点**：活路径在 `sampling.spot(60)` 前写 `Spot_6X_Start/End`+`Spot_7Y`；`photoscrape` capture 前写 `Photo_8Y_Target`。

### 2.4 待决
- **D2.1 逐带 vs 单值**：架构文档 §5.1 说「多带时点样位逐带变」。若一次运行多带，点表需按**带序**索引（`value` 变 `values[]`，注入时按当前带取）；若当前阶段单带，先单值。取决于 §3 的执行模型与「1样品=1带」是否=「1次运行1带」。
- **D2.2 step 时机**：PLC 的 `A60_spray`/`A34_cam` 在哪个 step 读 `Spot_*`/`Photo_8Y_Target`——**须等 PLC 步骤2迁移上真机后实测对齐**（写早了被旧值覆盖、写晚了读到陈旧）。

## 3. 必须先拍板的架构抉择 — 活路径采用 B 方案的方式

议题①②的代码落点，取决于**活路径（VM）如何采用 B 方案**。两条路：

| 选项 | 做法 | 取舍 |
|---|---|---|
| **R1. 改 VM 动作执行**（推荐） | 让 `sampling.aspirate` 的 `source_x/source_y` 经执行器**仿射翻译→写 `*_Target`**（替代旧 coordinate）；`sampling.spot` 注入 `Spot_*` 下发。孔位/板实例作为 VM 变量由下单注入。 | 不引入第二调度器；与现役 VM/operation 一致；改动集中在 executor + 动作定义。离线资产（plate_affine/calibration_service）作为被调用库复用。 |
| **R2. 接入 RecipeRunner/Scheduler** | 把路线 B 整体接进 bootstrap，样品级流程走 RecipeRunner，绕开 VM。 | 与现役 VM 双轨；RecipeRunner 的 `_transfer`/CNC 仍是占位；引入第二套并发模型。重复度高。 |

**建议 R1**：活路径已是 VM，B 方案的「单写者 + push_well + 复用 L2 握手」可作为**库**嵌入 VM 执行，不必另起调度。RecipeRunner 的价值（样品级编排）可后续以 VM operation（如 `01_full/ptlc_full.yaml`）承载。

> 这是**唯一阻塞**议题①②动手的决策点。定了 R1/R2，落地顺序即明确。
