# pTLC 自动化平台架构改造方案

## 1. 问题背景

当前 PLC 架构采用"工位级自治状态机"模式（`Enable → Busy/Step → Done`），适用于单资源串行工位（机械臂、收集、扫码等），大部分工位架构本身没有问题。

但展开平台是**多资源并行系统**（8个展缸），当前却被抽象为一个整体状态机：整个展开平台共享一组 `Expand_Busy/Step/Done`，导致一个板子展开时整个平台被占用，无法并行。核心瓶颈是**自治层级过高**。

## 2. 架构核心思想

不取消自治状态机，而是**自治粒度下沉**——从"整个平台自治"改为"每个展缸自治"，并增加上位机资源调度，形成**局部自治 + 全局调度**。

**职责划分：**

- **PLC（资源控制层）**：IO控制、联锁保护、实时动作、每个资源的原子动作状态机。不再负责整个实验流程调度。
- **上位机（任务调度层）**：任务队列、资源管理（展缸分配）、并行调度、工艺流程编排、异常恢复。

## 3. 原方案要点（已被下方正式决策修正）

原方案建议引入 `ST_ExpandTank` 结构体数组实现展缸实例化、采用"命令-状态"通信模型替代电平范式。这些具体技术方案**已在架构决策确认中被否决或调整**——改为"全局准备序列器 + per-tank 状态寄存器"，通信保持增强电平范式。具体以下方决策为准。

## 架构决策确认（2026-05-13）

### 决策背景
- 展开流程需支持多通道并行（8个展缸）
- 其他流程（点样、干燥等）维持单一自治状态机不变
- 展开时间30-60min，准备时间5-10min，并行收益显著

### 最终架构选择

| 决策项 | 结论 | 理由 |
|--------|------|------|
| 通信模型 | 增强电平范式（非命令-状态） | 与其他流程协议一致，开发成本最低 |
| 准备序列器 | 全局单序列器 → 渐进升级双序列器 | prep仅5-10min，单序列器几乎不损失并行收益 |
| 排液控制 | Per-tank独立触发信号 | 简单逻辑+可并行+不竞争prep资源 |
| 展开完成判定 | 视觉触发（当前用延时脚本代替） | 业务驱动，上位机侧控制 |
| 放板 | 机械臂自动（全局串行） | 但因prep已全局串行，不产生额外约束 |
| 样品绑定 | 分配时锁定，完成时释放，不可迁移 | 一致性优先 |

### 硬件拓扑确认

```
注射泵组1(SY-03B#1) ──→ [三通阀]──Tank1──[三通阀]──Tank2──[三通阀]──Tank3──[三通阀]──Tank4──→ 废液缸
注射泵组2(SY-03B#2) ──→ [三通阀]──Tank5──[三通阀]──Tank6──[三通阀]──Tank7──[三通阀]──Tank8──→ 废液缸
                                                                                          ↑
                                                                                      真空泵系统
```

- 每缸入口有独立三通阀，支持并行排液
- 排液使用真空泵，与注射泵（prep用）无资源竞争
- 机械臂全局共享，用于自动放板

### PLC侧新增变量协议

```st
(* === 新增：展缸状态跟踪 === *)
Tank_State      : ARRAY[1..8] OF INT;    // PLC→PC: 0=Idle, 10=Prepping, 40=Developing, 50=Draining, 99=Done, 90=Error
Tank_SampleID   : ARRAY[1..8] OF DINT;   // PC→PLC: 绑定样品ID（调试用）

(* === 新增：prep目标参数 === *)
Expand_Target_Tank : INT;                 // PC→PLC: 目标缸号(1-8)

(* === 新增：per-tank排液控制 === *)
Tank_Drain_Enable : ARRAY[1..8] OF BOOL;  // PC→PLC: 触发排液
Tank_Drain_Done   : ARRAY[1..8] OF BOOL;  // PLC→PC: 排液完成

(* === 保持不变：prep电平范式 === *)
(* Expand_Enable, Expand_Step, Expand_Busy, Expand_Done, Expand_Error, Expand_Reset *)
(* Expand_Mode_Flag, Expand_Group, Expand_Number, Expand_Confirm *)  // 注: Expand_Confirm 已废弃，详见 PLC_MultiTank_ST_Draft.md
```

### 上位机侧新增模块

| 模块 | 路径 | 职责 |
|------|------|------|
| ResourceManager | `core/resource_manager.py`(新增) | 展缸分配、状态同步、绑定管理 |
| DevelopStage改造 | `core/stages/develop.py`(改造) | 增加tank_id参数化，支持目标缸指定 |
| Scheduler改造 | `core/scheduler.py`(改造) | 展开阶段并行等待模式 |

### 样品→展缸绑定模型

```
① 分配点: DevelopStage.run()入口 → ResourceManager.allocate(sample_id) → tank_id
② 占用期: Steps 10-40全程，Tank状态Occupied(sample_id)，不可迁移
③ 释放点: Stage完成(Done/Error) → ResourceManager.release(tank_id) → 缸回归Idle池
```

绑定保证：唯一性（互斥锁）、稳定性（不可迁移）、原子性（asyncio.Lock）、可审计（事件日志）

### 执行时序图（稳态运行）

```
PC:  allocate(S1)→Tank3  |  写Target=3, Enable=TRUE
PLC:                      |  Tank_State[3]=10, 执行prep Steps10-35
PLC:                      |  Tank_State[3]=40, Expand_Done=TRUE, Busy=FALSE
PC:  allocate(S2)→Tank4  |  写Target=4, Enable=TRUE
PLC:                      |  Tank_State[4]=10, 执行prep...
    ... Tank3 展开中(30-60min) ...
Vision: Tank3展开完成      |  通知PC
PC:                       |  写Tank_Drain_Enable[3]=TRUE
PLC:                      |  切阀+开真空, Tank_State[3]=50→99, Drain_Done[3]=TRUE
PC:  release(Tank3)       |  Tank3回归Idle池
```

### Expand_Done语义变更

- **旧语义**: 整个展开流程（prep+develop+drain）完成
- **新语义**: 当前prep指令执行完毕，目标缸已进入展开阶段（Tank_State=40）
- **实际展开完成**: 由Tank_State[i]从40转为99标识（视觉触发排液完成后）

### 渐进实施路线

1. Phase 1: 全局单序列器 + Tank_State跟踪 + 单缸全栈验证
2. Phase 2: 双缸交错验证（prep A → A展开 → prep B → 等待A/B完成）
3. Phase 3: 升级为双序列器（跨组并行prep）+ 8缸压力测试

### 对架构讨论.md原方案的修正

1. **不采用** 8个完全独立PLC状态机 → 改为"全局准备序列器 + per-tank状态寄存器"
2. **不采用** 命令-状态通信模型升级 → 保持增强电平范式
3. **不采用** 第四阶段"拆分原子动作FB" → prep必须串行，拆分不提升并行度
