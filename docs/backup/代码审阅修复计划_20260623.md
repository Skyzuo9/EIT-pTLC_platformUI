## 第一性原理：缺陷的两条主线

1. **"写伺服目标"存在两条入口，安全基础设施未统一。** `PointsService.push_target/set_target_value/set_servo_position` 三处写前都做 `[min_limit, max_limit]` 校验，而 `CalibrationService.push_well` 绕过它直写 `*_Target`，既无限位也拿不到限位值。→ 修复应让"写 Target"收敛成**唯一一条经限位校验的入口**，标定/recipe 都复用它，而不是各自直写节点（修 #1，并为 #3 同源加固）。
2. **"验证后再改状态"的次序在两处被破坏。** 标定 commit 先改内存后 solve；L2 等待循环先 `int()` 后才可能发现字段为 None。→ 修复统一为"先校验/解析成功，再改共享状态/推进"。

执行按批次推进：**P0 安全/正确性（#1–#4）→ P1 健壮性（#5–#6）→ P2 潜伏与契约（#7–#9）→ P3 可维护性（#10）**。每项含独立单测，互不阻塞，可分别提交。

## P0 — 安全 / 正确性（必修）

### #1 🔴 `push_well` 直写伺服 Target，无软限位钳制 — 物理撞机风险

- **位置**：[calibration_service.py:83-91](../eit_ptlc/controller/calibration_service.py#L83-L91)
- **根因**：`push_well` 由 `well_target` 算出 X/Y 后直接 `write_variable("*_Target", ...)`，全路径无限位检查；`_warn_if_off_nominal` 仅 `log.warning` 不抛异常；`CalibrationService.__init__` 根本未持有 `min_limit/max_limit`。边角孔位标定偏差 → 越程目标写入 → 伺服撞硬限位。
- **修复方案（推荐：收敛到单一带限位的写入口）**：
  1. 让 `CalibrationService` 通过 `PointsService`（或共享的"带限位写 Target"helper）下发，而非持有裸 driver 直写。`push_well` 算出 (x, y) 后，复用 `PointsService` 已有的限位校验逻辑写入对应轴的 `*_Target` 节点。
  2. 若短期不便引入 `PointsService` 依赖，则至少给 `CalibrationService` 注入对应轴的 `(min_limit, max_limit)`（来自 `points.yaml`），在 `write_variable` 前做与 `push_target` 一致的 `if not (lo <= v <= hi): raise ValueError(...)`。
  3. 越程时**拒绝下发并抛错**（不静默 clamp，避免把"标错"掩盖成"贴边"）。
- **测试**：构造一个仿射使边角孔 X/Y 越程 → 断言 `push_well` 抛 `ValueError` 且**未发生** `write_variable`（mock driver 校验零写入）。
- **风险**：低；新增的是拒绝路径，正常标定不受影响。

  - 故强制显式 status 只增流程摩擦、不增安全。
- **修复方案（降级）**：仅在 `_build_supplemental`（line 354）与 `with_derived_points`（line 173）的默认值处加注释，说明"派生点省略 status 即视为 validated + move_l（确定性几何派生，无需逐点示教）"，让未来作者知晓语义。**不改默认值、不迁移数据。**

### #3 🔴 `commit()` 先改内存后校验 — 退化输入污染已有标定

- **位置**：[calibration_service.py:74-80](../eit_ptlc/controller/calibration_service.py#L74-L80)

  - 实现选项 B：`commit` 内先构造临时 `PlateCalibration`/调用 `solve_affine(points)` 校验，成功后再 `set_calibration`。
- **测试**：给已标定实例提交 3 个共线点 → 断言抛 `ValueError` **且**该实例原标定仍可用（`transform()`/`targets()` 正常返回旧结果）。
- **风险**：低；纯次序调整。

### #4 🟠 L2 等待循环 `int(snap['State'])` 遇 None 抛 TypeError — 击穿"结果未知不重发"契约

- **位置**：[plc_controller.py:267-270](../eit_ptlc/controller/plc_controller.py#L267-L270)
- **根因**：镜像 seeding（[opcua_driver.py:674](../eit_ptlc/driver/opcua_driver.py#L674)）与 `refresh_mirror`（[opcua_driver.py:615](../eit_ptlc/driver/opcua_driver.py#L615)）均 `except Exception: pass`；首读瞬时失败 → 字段缺失 → `cached_many` 返回 None → `int(None)` 抛 `TypeError`。该异常非 `PLCActionOutcomeUnknown`，逃逸 `_execute_one`，绕过看门狗"结果未知、勿重发"处理。
- **修复方案**：在 `int()` 之前对快照字段做 None 守卫——若 `snap["State"]/AcceptedSeq/CompletedSeq` 任一为 None，视为"尚未拿到镜像"，`continue` 进入下一轮等待（由 `wait_change`/poll 唤醒），并让停滞看门狗（`stall_timeout`）兜住"始终读不到"的病态情形。
  ```python
  snap = self._cached_l2(prefix)
  if snap.get("State") is None or snap.get("AcceptedSeq") is None or snap.get("CompletedSeq") is None:
      # 镜像尚未 seed（首读瞬时失败被吞）；等下一次订阅变化/poll，停滞看门狗兜底
      ... # 走到循环末尾的 wait 分支，而非 int(None)
      continue
  state = PLCActionState(int(snap["State"]))
  ```
  注意 `continue` 前要保证停滞看门狗仍会推进（`last_progress` 不更新即可正常超时为 `PLCActionOutcomeUnknown`）。
- **测试**：mock `_cached_l2` 首轮返回 `{"State": None, ...}`、次轮返回正常终态 → 断言不抛 `TypeError` 且最终正常完成；持续返回 None → 断言最终抛 `PLCActionOutcomeUnknown`（非 `TypeError`）。

## P1 — 健壮性

### #5 🟠 `read_frame` 在持续流错位时自递归 — 栈溢出崩溃反馈线程

- **位置**：[dobot_tcp_driver.py:191-194](../eit_ptlc/driver/dobot_tcp_driver.py#L191-L194)（`if frame is None: return self.read_frame()`）
- **根因**：真递归（非循环），Python 无尾调用优化。30004 流持续失步/噪声（每个候选 parse 失败）时，每次调用阻塞读取后再递归，栈无限增长 → `RecursionError` 崩溃反馈读取线程，而非干净的 `RobotTransportError`。
- **修复方案**：把方法体整体包进 `while True:`，原"递归取下一帧"改为 `continue`：
  ```python
  def read_frame(self) -> DobotFeedbackFrame:
      while True:
          # 1) 阻塞读到至少一帧
          while len(self._buffer) < FEEDBACK_SIZE: ...
          # 2) 非阻塞排空 ...
          # 3) 逐帧解析丢弃，保留最新对齐帧 ...
          if frame is None:
              continue   # 排空所得全是错位字节，回到顶部再阻塞取一帧
          return frame
  ```
  forward progress 由步骤 1 的阻塞读保证（每轮至少消费 FEEDBACK_SIZE 新字节），循环不增长栈。
- **测试**：用 fake socket 先吐若干轮纯错位字节、再吐一个合法帧 → 断言 `read_frame` 返回该帧且不抛 `RecursionError`。

### #6 🟠 派生点缺 `offset` 键抛裸 KeyError — bootstrap 启动报错晦涩

- **位置**：[point_registry.py:275-282](../eit_ptlc/controller/point_registry.py#L275-L282)
- **根因**：`has_offset` 只看 `base_point` 是否存在、不查 `offset` 键；为真时 `offset_raw = record["offset"]` 直接下标。补充点若有 `base_point` 但漏写 `offset`，抛裸 `KeyError: 'offset'` 而非本函数统一的描述性 `ValueError`，在实时启动路径（[bootstrap.py:201](../eit_ptlc/runtime/bootstrap.py#L201)）让 bootstrap 以无提示错误中止。
- **现状**：当前 meta 中 0 条命中（纯防御性），但文件人工/工具编辑，手误可达。
- **修复方案**：在 `has_offset` 分支取值前显式检查：
  ```python
  if has_offset:
      if "offset" not in record:
          raise ValueError(f"supplement point {record['point_id']} 声明了 base_point 但缺少 offset")
      offset_raw = record["offset"]
  ```
- **测试**：构造 `{point_id, workstation, role, base_point}` 无 offset 的补充点 → 断言抛 `ValueError`（含 point_id）而非 `KeyError`。

### #9 🟡 `POST /api/robot/speed_factor` 缺 ratio 时返回 HTTP 200 + status=REJECTED

- **位置**：[app.py:194-200](../eit_ptlc/api/app.py#L194-L200)
- **根因**：无条件转发 `body.get('ratio')`，缺失为 None → action 校验 REJECTED；`action_result_to_dto` 不设状态码 → HTTP 200。前端 `RobotJogPanel.vue` 会渲染 REJECTED（非静默成功），且输入为 `v-model.number`，故仅畸形直接调用可触发。**低危，主要防未来中控直连 API（只判 HTTP 码的调用方）。**
- **修复方案**：在路由层对必填 `ratio` 做前置校验，缺失/非数值返回 `HTTP 422/400`，使 HTTP 码与 result.status 一致。本次仅修该路由，不做"REJECTED 统一映射非 2xx"（影响面大、需前端配合）。
- **测试**：POST 无 ratio → 断言 4xx；正常 ratio → 200。
