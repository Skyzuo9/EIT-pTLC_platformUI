# 视觉调试台审查修复实施计划

> 日期：2026-06-30
> 活动工作区：`EIT_Project-Next`
> 分支：`codex/ui-upper-next`
> 状态：实施前修复计划（本文件不代表真机验收完成）

## 1. 背景与目标

当前视觉调试台已经实现了部分页面、API、固定工作区、图像质量诊断和双帧分析骨架，但代码审查表明：

1. 视觉调试服务尚未装配到运行时，现有 API 实际会返回 `503`。
2. 前端、调试服务和真实相机控制器之间存在多处字段及调用签名错配。
3. `uv_on_time_ms` 目前只是事后统计值，没有真正控制 UV 总点亮时间。
4. 抓图异常路径存在取消硬截止且未关灯的风险，不满足 UV 光源最长工作时间不超过 2 秒的安全要求。
5. 拍照质量检测使用了不适合现有荧光图像的板框假设，真实样图无法得到板中心、旋转和透视指标。

本轮目标不是接入生产流程，而是完成一个安全、可验证、便于人与 Codex 等 Agent 协作的独立视觉调试模块：

- Before/After 均可独立拍摄或加载已有图片。
- 可调整曝光、增益、UV 总点亮时间。
- 可检查板位置、旋转、透视、曝光和清晰度。
- 可调整双帧识别参数并检查原点、溶剂前沿、条带、Rf 和中间评分证据。
- UI、Codex 和后端共用一份稳定的调试状态和产物。
- 不修改或依赖生产 operation。

## 2. 第一性原理约束

### 2.1 UV 安全必须是驱动不变量

不能依赖前端输入范围或操作员注意力保证 UV 安全。无论调用来自 UI、API、Codex、测试脚本还是未来生产流程，底层驱动都必须执行同一套参数校验和关灯逻辑。

必须满足：

```text
exposure_time_us > 0
uv_on_time_ms > 0
exposure_time_us / 1000 <= uv_on_time_ms
uv_on_time_ms <= UV_WORKING_LIMIT_MS
UV_WORKING_LIMIT_MS < UV_HARD_LIMIT_MS
UV_HARD_LIMIT_MS <= 2000
```

初始建议：

```text
UV_WORKING_LIMIT_MS = 1800
UV_HARD_LIMIT_MS = 2000
```

工作上限为系统和 SDK 抖动留出余量；硬截止不得通过配置放宽到 2 秒以上。

### 2.2 一次拍照必须是不可拆分的原子操作

不提供独立 UV 开关，不允许调用方直接控制 Line1。

目标时序：

```text
连接相机
→ 强制 Line1 OFF 并确认
→ 配置曝光、增益和软件触发
→ stream_on
→ Line1 ON
→ 在设定 UV 窗口内触发并获取目标帧
→ Line1 OFF 并确认
→ 转换和保存图像
```

任何异常、超时或取消路径都必须尝试关灯。只有确认关灯完成后，才允许释放相机单写锁并接受下一次拍照。

### 2.3 调试必须复用同一真实路径

- 拍照调试复用 `CameraController` / `DahengCameraService`。
- 双帧识别复用 `VisionService` / `tlc_analyze.process_pair()`。
- 不新写第二套相机驱动或识别算法。
- 临时调参通过单次 overrides 生效，不自动写入生产配置。

### 2.4 诊断结果先做测量，不武断给合格结论

在没有现场重复数据和接受区间前，中心偏移、亮度、清晰度等只展示数值及前后变化，不提前编造通用红绿阈值。

## 4. 目标架构

### 4.1 固定工作区

保持单一工作区，不引入数据库和无限历史：

```text
eit_ptlc/var/vision_debug/
  state.json
  before.jpg
  after.jpg
  before_quality.png
  after_quality.png
  result/
    summary.json
    score.png
    annotated.png
```

`state.json` 是 UI 和 Agent 的唯一状态入口，至少包含：

```json
{
  "revision": 1,
  "updated_at": "ISO-8601",
  "camera_params": {
    "exposure_time_us": 1000000,
    "gain": 1.0,
    "uv_on_time_ms": 1000
  },
  "recognition_params": {
    "image_plate_orientation": "rot180",
    "auto_rectify_tilt": true,
    "rectify_min_angle_deg": 0.5,
    "min_row_score": 5.0
  },
  "before": {},
  "after": {},
  "capture_quality": {},
  "uv_timing": {},
  "analysis": null,
  "error": null
}
```

### 4.2 API

保留以下接口：

- `GET /api/vision/debug/state`
- `POST /api/vision/debug/capture`
- `POST /api/vision/debug/upload/{role}`
- `POST /api/vision/debug/analyze`
- `GET /api/vision/debug/file/{filename}`

请求必须改为严格 DTO/Pydantic 模型，不再用裸 `dict` 静默忽略未知字段。

物理拍照失败、输入非法和分析失败必须返回明确的非 2xx 状态或统一的 `ok=false` 契约，不能让调用方把 HTTP 200 当成成功。

### 4.3 前端

保持单个 `VisionDebugView.vue`，不新增 Pinia store。

页面至少展示：

- Before/After 原图。
- Before/After 质量叠加图。
- 曝光、增益、UV 总点亮时间。
- 请求与实际 UV 点亮时间、关灯结果和是否超限。
- 板中心偏移、旋转、透视、四边留白、亮度、过曝、欠曝、清晰度。
- 差异评分图。
- 原点与溶剂前沿来源。
- Band ID、Rf、质心、宽度、面积。

所有图片 URL 都必须附带 `?rev=<revision>`，避免覆盖文件后浏览器继续显示缓存旧图。

页面至少提供“刷新状态”按钮；建议 1 秒低频轮询 state，使 Codex 通过 API 重跑后，页面可自动更新。轮询只读状态，不触发相机。

## 5. 分阶段实施

## 阶段 A：修复 UV 安全与真实相机时序

### A1. 固化参数模型

修改：

- `eit_ptlc/config/models.py`
- `eit_ptlc/config/loader.py`
- `eit_ptlc/config/app.yaml`
- `eit_ptlc/driver/daheng_capture.py`

任务：

1. 将 `trigger_source`、`uv_on_time_ms`、硬截止常量加入正式模型。
2. 硬截止上限使用代码常量，不允许由普通请求放宽。
3. 增加统一参数校验函数，在打开相机和开启 UV 前执行。
4. 保持单位统一：
   - 曝光：µs
   - UV：ms

### A2. 修正软件触发

任务：

1. 设置 `TriggerMode=On`。
2. 设置 `TriggerSource=Software`。
3. 在 Line1 开启后显式发送 `TriggerSoftware` 命令。
4. 验证返回帧号/时间戳属于本次触发。
5. 软件触发不受支持时 fail-closed，不自动回退到可能返回旧帧的连续采集路径。

### A3. 修正关灯逻辑

任务：

1. `light_on` 初始状态必须为 `False`，只有开灯成功后才置 `True`。
2. 最内层 `finally` 无条件尝试关闭 Line1。
3. 关灯成功前不得取消硬截止后备。
4. 首次关灯失败时保留后备定时器并再次尝试。
5. 初始强制 OFF 失败、ON 失败或最终 OFF 失败都必须 fail-closed。
6. `actual_uv_on_ms` 在关灯调用返回后计算，并明确是软件命令窗口；真机还需测量物理电平。

### A4. 修正取消与锁

任务：

1. HTTP/asyncio 任务取消后，不得立即释放相机锁。
2. 等待后台 SDK 线程完成清理和关灯后再释放锁。
3. 同时到来的第二个拍照请求返回 BUSY 或安全排队，不得进入第二条相机线程。

### 阶段 A 验收门

- 非法参数在开灯前被拒绝。
- 正常、超时、异常帧、转换失败、保存失败、请求取消均执行 OFF。
- Software Trigger 确实发送。
- 两个并发请求不能同时进入 SDK。
- 未完成假 SDK 安全测试前禁止真机 UV 测试。

## 阶段 B：补齐配置和运行时装配

### B1. 增加视觉调试配置模型

新增 `VisionDebugCfg`，并加入 `AppConfig` 与 `load_config()`。

配置只保留真正需要的字段：

- `workspace_dir`
- 默认相机参数
- 默认识别参数

硬安全上限不作为可自由放宽的 YAML 参数。

### B2. 装配调试服务

修改 `eit_ptlc/runtime/bootstrap.py`：

1. 复用已经构造的相机和视觉实例。
2. 创建 `VisionDebugService`。
3. 注入 `app.state.vision_debug`。
4. 确保 sim 模式仍可用 Mock 相机，real 模式才访问大恒相机。

### B3. 统一相机调用契约

`VisionDebugService` 不再自创 `capture(exposure_time_us=...)` 接口。

应调用正式接口，例如：

```python
await camera.capture_with_timing(
    sample_id="vision-debug",
    save_dir=workspace,
    filename="before.jpg",
    params={
        "exposure_time": ...,
        "gain": ...,
        "uv_on_time_ms": ...,
    },
)
```

避免同时维护 `exposure_time` 和 `exposure_time_us` 两套运行期键名；DTO 可使用带单位的名字，但进入驱动前必须集中转换一次。

### 阶段 B 验收门

- `GET /api/vision/debug/state` 不再返回 503。
- sim 模式能完成 Mock Before/After 拍摄。
- real 模式调用签名与 CameraController/DahengCameraService 一致。
- 增加真实 `create_app/bootstrap/API` 集成测试，不能只测试孤立 Service。

## 阶段 C：修复状态与文件一致性

任务：

1. 新拍摄或上传任一图片后：
   - 清空 `analysis`
   - 删除或失效旧 `result/*`
   - 增加 `revision`
2. 分析失败时清空旧成功结果，不保留可被误读的 Band 和图片 URL。

   - 仅接受 JPEG/PNG 等明确白名单。

4. `GET state` 返回稳定快照，不把内部可变 dict 直接暴露给并发调用方。
5. 文件路径继续使用白名单和工作区边界检查。

### 阶段 C 验收门

- 不在缺少重复数据时定义拍照质量“合格/不合格”阈值。

## 8. 完成定义

只有同时满足以下条件，视觉调试台才可标记为完成：

- 调试 API 已真实装配，前后端字段完全一致。
- Before/After 拍摄和上传均可工作。
- UV 参数真实控制点亮窗口，任何异常路径均关灯。
- Line1 物理高电平已证明不超过 2 秒。
- 真实样图可以得到板位置、旋转和透视诊断。
- 条带、原点、溶剂前沿、Rf、评分图和质量指标均可在页面查看。
- Codex 可读取稳定 state 和图片，通过 API 重跑后页面自动更新。
- 新增专项测试通过。
- 完整测试套件状态已说明且无未归因回归。
- 生产 operation 保持无差异。
