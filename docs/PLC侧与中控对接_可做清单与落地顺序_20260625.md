## 0. 两个定调结论（先读）

1. **中控对接已不是"架构阻塞"，只剩"契约阻塞"。**
   0623 稿纠结的 R1/R2 抉择（改 VM executor vs 接 RecipeRunner+Scheduler）已被**删除消解**——`operation/recipe.py` + `scheduler.py` 在 commit `14083c5` 物理删除，现 `eit_ptlc/operation/` 仅余 `consumable_manager / resource_manager / resources / vm / robot_routes`，全工程 `RecipeRunner/Scheduler/SampleRequest` 零命中。**R1（改 VM executor）成为唯一且默认路径，可直接动手。** B 方案的"库"部分（`calibration_service.push_well` / `plate_affine`）幸存且已接进 [bootstrap.py:226](../eit_ptlc/runtime/bootstrap.py#L226)，直接复用。

   三份交付稿要求的主体节点（B 方案 `*_Target` / `*_ActPos`、Rail_L2 字段、Rail_Sync 节点、4X 清洗位 flat 节点）已在当前 `.project` 中核实；Mock 按 `node_map` 同构创建。缺口：① Mock 缺部分 FSM 行为（sim 跑不出完整闭环）；② 5Z 仍未在 PLC 工程命中；③ 4X 清洗位 PLC 已改读但运行期还没在 `sampling.clean` 前编排下发。

### D. 需中控给契约才能定稿

A6 解析骨架可先做双解占位，但**生产校验严格度 + 端到端联调**需以下定稿：

- **D1.1 孔位表示法**：大 JSON 用 `(row,col)` 还是孔号？内部已统一 `Well(row,col)`（[calibration_routes.py:46-50](../eit_ptlc/api/calibration_routes.py#L46)），解析层可双解，但"拒绝越界/非法 well"的最终校验需锁定唯一表示法。

## 2. 建议起手顺序

1. **A1（S，地基）** — 不接 `mirror_on_done` 则后续所有 sim 验证（标定采点 / ActPos 回读 / 按孔下发）在 sim 下恒读 `0.0` 失真，无法自证。一次 bootstrap 接线解锁最多下游验证。
   > 注意：`Spot_6X/7Y_Target` 与 `Photo_8Y_Target` 分属 Sampling 与 PhotoScrape 两前缀，映射对须按真实消费工位分配。
2. **A2 + A3（均 S，清场）** — A2 补已下载节点的真缺口（否则清洗位去 0），与议题② 范式一致零风险；A3 消除议题①的假阻塞认知。
3. **A4 → A5 → A6（议题① R1 实质推进，全程不依赖中控契约）** — 把孔位提为 VM 变量 → executor 调 `push_well` 替代旧 coordinate → orders 解析骨架双解占位。推到"只差中控填变量 + PLC A50 改读"的临界状态，为 C1（PLC）与 D1.1/D1.2（中控）铺好接口。等中控给契约时只需收紧 A6 校验严格度即可端到端联调。

> B 类（Mock Rail_Sync）价值在双源同步先验，不阻塞议题①主线，可在第 3 步之后或并行穿插。
